<h1>CSS Scroll-Driven Animations: The Complete Guide with Live Demos</h1>

<p>For as long as CSS has had <code>@keyframes</code>, animation progress has meant one thing: time. An animation starts, a clock runs, the animation ends &mdash; scroll position never entered the equation, which is exactly why every "fade in as you scroll" or "progress bar that fills as you read" effect has always needed JavaScript to poll or observe the scroll position and translate it into style changes by hand. The <code>animation-timeline</code> property changes that at the spec level: it lets a normal <code>@keyframes</code> animation's progress be driven by scroll position instead of time. <code>animation-timeline: scroll()</code> ties an animation's 0%&ndash;100% progress to how far a scroll container has been scrolled through its own range. <code>animation-timeline: view()</code> ties it to an element's own visibility as it physically crosses the scrollport &mdash; entering at 0%, fully progressed by the time it has crossed through to exiting. Neither one runs a single line of JavaScript to do it.</p>

<p>The 8 demos below are all live and interactive, and every one of them needs real scroll distance to show its effect &mdash; scroll inside each embed, not just around the page. Each embed also has a <strong>Fork &amp; Edit</strong> button that opens the exact code, already running, in <a href="https://fwdtools.com/ui-snippets/mycode/">My Code</a> &mdash; FWD Tools' free in-browser editor. Change an <code>animation-range</code>, swap <code>scroll()</code> for <code>view()</code>, delete <code>animation-fill-mode: both</code> and watch what breaks &mdash; that's the fastest way to build real intuition about a spec feature this new.</p>

<p>New to CSS in general, or want a guided path through the fundamentals these demos build on? The <a href="https://fwdtools.com/css-playground/">CSS Playground</a> is FWD Tools' free, click-based, in-browser sandbox for exactly this kind of experimentation.</p>

<h2>How this compares to GSAP ScrollTrigger</h2>

<p>If you've read FWD Tools' <a href="https://www.webdevpuneet.com/search/label/GSAP">GSAP ScrollTrigger tutorial</a>, the mental model below will feel familiar &mdash; <code>scroll()</code> is conceptually close to ScrollTrigger's <code>scrub</code> mode, and <code>view()</code> plus <code>animation-range</code> is close to a trigger's <code>start</code>/<code>end</code> strings. The honest difference is support and control: native CSS scroll-driven animation ships today only in Chromium browsers (Chrome and Edge), runs entirely off the main thread with zero JavaScript, and can't sequence timelines, stagger elements, or read scroll velocity the way ScrollTrigger can; GSAP ScrollTrigger works cross-browser today, right now, with far more scripting power, at the cost of shipping a library and running its logic on every scroll frame. This post's job isn't to declare a winner &mdash; it's to give the pure-CSS mechanism the same thorough treatment, since knowing both means reaching for whichever one actually fits a given browser matrix and effect.</p>

<h2>1. The core scroll() timeline</h2>

<p>Scroll down inside this frame. The bar below fills from 0% to 100% width purely because <code>animation-timeline: scroll()</code> ties its <code>@keyframes</code> progress to how far you've scrolled through the whole frame &mdash; no scroll event listener, no <code>requestAnimationFrame</code>, no GSAP <code>scrub</code>.</p>

<iframe src="https://fwdtools.com/demos/a1/36/1.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Core scroll() Timeline Demo by FWD Tools"></iframe>

<p><strong>The rule:</strong></p>

<pre><code class="language-css">.fill {
  transform-origin: left center;
  animation: grow linear;
  animation-timeline: scroll();   /* progress = 0%-100% of scroll range */
}

@keyframes grow {
  from { transform: scaleX(0); }
  to   { transform: scaleX(1); }
}</code></pre>

<p>Setting <code>animation-timeline</code> to anything other than its default value of <code>auto</code> fundamentally changes what drives an animation's progress. Normally, <code>animation-duration</code> and the system clock decide how far into <code>@keyframes</code> the browser currently is; with a scroll timeline in place, the clock is disconnected entirely and progress instead becomes a direct function of the scroll offset of a scroll container, remapped to a 0&ndash;1 range across that container's full scrollable distance. <code>animation-duration</code> still has to be present for the animation to be considered valid, but its actual numeric value stops mattering once a non-<code>auto</code> timeline takes over &mdash; <code>linear</code> easing is almost always what you want too, since the browser is already doing the interpolation continuously as you scroll, and any other easing curve would double up. The equivalent JavaScript approach &mdash; a <code>scroll</code> listener computing a percentage and writing a <code>transform</code> style on every frame, or a GSAP tween with <code>scrub: true</code> &mdash; is doing by hand exactly what this one CSS declaration now does natively, off the main thread.</p>

<p><strong>Best for:</strong> reading-progress bars, scroll indicators, and any effect that should track the page's overall scroll position rather than one element's visibility. <strong>Tip:</strong> without an explicit source, <code>scroll()</code> defaults to the nearest scrollable ancestor &mdash; demo #2 covers exactly when that default is and isn't what you want.</p>

<h2>2. scroll(root) vs. scroll(nearest)</h2>

<p>Scroll this whole frame first, then scroll <em>inside</em> the gray box further down. Watch which bar reacts to which scroll &mdash; the two bars use identical <code>@keyframes</code> but different scroll sources.</p>

<iframe src="https://fwdtools.com/demos/a1/36/2.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="scroll(root) vs scroll(nearest) Demo by FWD Tools"></iframe>

<p><strong>The rule:</strong></p>

<pre><code class="language-css">.fillRoot {
  animation: grow linear;
  animation-timeline: scroll(root);      /* always the document's own scroller */
}

.fillNearest {
  animation: grow linear;
  animation-timeline: scroll(nearest);   /* closest scrollable ancestor, wherever it is */
}</code></pre>

<p><code>scroll()</code> takes an optional scroller argument &mdash; <code>nearest</code> (the default), <code>root</code>, or <code>self</code> &mdash; because "scroll position" is meaningless until you say whose scroll position. <code>nearest</code> walks up from the animated element through its ancestors and picks the first one that actually scrolls, which is usually what you want for a component embedded somewhere in a layout, but it silently changes meaning if that component ever gets moved inside a new scrollable wrapper. <code>root</code> always means the document's own scroller, full stop, regardless of how deeply nested the animated element is in the DOM &mdash; useful for a global reading-progress bar that has to track the whole page even if it happens to render inside several nested containers. <code>self</code> means the timeline is generated by the element's own scrolling, so the element has to be a scroll container animating itself, a much rarer case. Getting this argument wrong doesn't throw an error; it just silently attaches your animation to the wrong scroll range, which is why this pairs so directly with demo #1's default behavior.</p>

<p><strong>Best for:</strong> deliberately choosing between "this effect belongs to the page" (<code>root</code>) and "this effect belongs to its own local scroll container" (<code>nearest</code>) rather than relying on whichever one the DOM happens to produce. <strong>Tip:</strong> when a component might get moved into a different layout later, <code>root</code> is the more future-proof choice unless you specifically want the local-container behavior.</p>

<h2>3. The core view() timeline</h2>

<p>Scroll down. The card below fades and slides in purely because it is entering this frame's own scrollport &mdash; not because a scroll listener fired, not because an <code>IntersectionObserver</code> callback ran, but because <code>animation-timeline: view()</code> ties its progress directly to its own position crossing the viewport.</p>

<iframe src="https://fwdtools.com/demos/a1/36/3.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Core view() Timeline Demo by FWD Tools"></iframe>

<p><strong>The rule:</strong></p>

<pre><code class="language-css">.card {
  animation: reveal linear both;
  animation-timeline: view();   /* progress = this element's own visibility */
}

@keyframes reveal {
  from { opacity: 0; transform: translateY(40px); }
  to   { opacity: 1; transform: translateY(0); }
}</code></pre>

<p><code>view()</code> is a fundamentally different kind of timeline from <code>scroll()</code>: instead of tracking a scroll container's own offset, it tracks the animated element's position relative to its scrollport as that scrollport scrolls, regardless of how far the page has scrolled overall. Progress 0% is the moment the element's leading edge first touches the scrollport; progress 100% is the moment its trailing edge has fully crossed through the far side. Everything in between is computed purely from geometry &mdash; where the element's box currently sits relative to the viewport &mdash; recalculated continuously as either the element or the scrollport moves. This is the direct native replacement for the single most common piece of scroll JavaScript ever written: an <code>IntersectionObserver</code> toggling a class that a CSS transition then animates. That pattern needs an observer instance, a callback, and a class toggle running in script; <code>view()</code> needs one declaration and does the geometry work in the browser's own layout and compositing pipeline instead.</p>

<p><strong>Best for:</strong> reveal-on-scroll effects, staggered content that should animate in as the reader reaches it, and any "this appeared in the viewport" effect that previously meant reaching for <code>IntersectionObserver</code>. <strong>Tip:</strong> always pair <code>view()</code> with an explicit fill mode &mdash; demo #8 shows exactly what goes wrong without one.</p>

<h2>4. animation-range: controlling where the timeline runs</h2>

<p>Both boxes below use the same <code>@keyframes</code> and the same <code>view()</code> timeline. Scroll slowly and watch the amber box finish appearing much sooner than the indigo one &mdash; only their <code>animation-range</code> differs.</p>

<iframe src="https://fwdtools.com/demos/a1/36/4.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="animation-range on a view() Timeline Demo by FWD Tools"></iframe>

<p><strong>The rule:</strong></p>

<pre><code class="language-css">.boxDefault {
  animation: reveal linear both;
  animation-timeline: view();       /* runs across the whole view timeline */
}

.boxRange {
  animation: reveal linear both;
  animation-timeline: view();
  animation-range: entry 0% cover 30%;   /* finished 30% into the "cover" phase */
}</code></pre>

<p>A <code>view()</code> timeline is internally divided into named ranges &mdash; <code>entry</code> (the element entering the scrollport), <code>contain</code> (fully contained within it), <code>exit</code> (leaving it), and <code>cover</code>/<code>contain</code> variants that span combinations of those &mdash; and <code>animation-range</code> is what lets you say "run my <code>@keyframes</code> across only <em>this</em> slice of that timeline" instead of the whole thing. <code>entry 0% cover 30%</code> means: start the moment the element begins entering (0% into the <code>entry</code> phase) and finish once the element has moved 30% of the way through its full <code>cover</code> range &mdash; a short, early-finishing animation compared to the default, which stretches the same <code>@keyframes</code> across the entire timeline from first appearance to last disappearance. This is the direct CSS-native equivalent of ScrollTrigger's <code>start</code>/<code>end</code> strings, just expressed as named phases of visibility instead of pixel or percentage offsets against the viewport.</p>

<p><strong>Best for:</strong> making a reveal finish quickly after an element appears rather than dragging out across its entire time on screen &mdash; the difference between "arrives," and "is still arriving" halfway down the page. <strong>Tip:</strong> the range keyword and percentage can be applied independently to the start and end &mdash; <code>animation-range-start</code> and <code>animation-range-end</code> exist as longhands if you only need to change one side.</p>

<h2>5. Named scroll-timeline: decoupling animator from scroller</h2>

<p>The dot pinned near the top of this frame is driven entirely by the scroll position of the gray box further down &mdash; a completely different element, nowhere near it in the DOM. Scroll inside the box and watch the dot move.</p>

<iframe src="https://fwdtools.com/demos/a1/36/5.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Named scroll-timeline Demo by FWD Tools"></iframe>

<p><strong>The rule:</strong></p>

<pre><code class="language-css">.scrollBox {
  overflow-y: auto;
  scroll-timeline-name: --box;   /* declare a name on the scroller */
}

.dot {
  animation: slide linear;
  animation-timeline: --box;     /* a different element references it by name */
}</code></pre>

<p>Everything in demos #1&ndash;4 attaches a timeline to the same element it animates, or takes it from an unnamed ancestor found by walking the DOM. Named timelines remove that coupling entirely. <code>scroll-timeline-name</code> (or <code>view-timeline-name</code>) declares a custom-ident, prefixed with <code>--</code> exactly like a custom property, on whichever element actually scrolls; any element anywhere else in the document &mdash; a sibling, a cousin, something in a completely unrelated part of the tree &mdash; can then set its own <code>animation-timeline</code> to that same name and have its <code>@keyframes</code> driven by that scroller's progress. This is the piece that makes scroll-driven CSS genuinely composable rather than positionally constrained: a header indicator, a fixed sidebar element, or a completely separate widget can all react to one content area's scroll without any of them needing to be its ancestor, descendant, or even nearby in the markup.</p>

<p><strong>Best for:</strong> a global progress indicator, sidebar element, or header widget that needs to react to one specific scroll container's progress without being nested inside it. <strong>Tip:</strong> the name has to match exactly, including the leading <code>--</code>, on both the declaring element and every element referencing it &mdash; there's no error if it doesn't match, the referencing animation simply never runs.</p>

<h2>6. A horizontal scroll-linked gallery</h2>

<p>Scroll the filmstrip below sideways. The progress bar pinned underneath it tracks the gallery's own horizontal scroll via <code>animation-timeline: scroll(inline)</code> &mdash; not the page's vertical scroll, which this frame doesn't even have.</p>

<iframe src="https://fwdtools.com/demos/a1/36/6.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Horizontal scroll() Gallery Demo by FWD Tools"></iframe>

<p><strong>The rule:</strong></p>

<pre><code class="language-css">.galleryWrap {
  overflow-x: auto;   /* the scroll container */
}

.fill {
  animation: grow linear;
  animation-timeline: scroll(inline);   /* the axis, not the scroller */
}</code></pre>

<p><code>scroll()</code>'s argument isn't limited to a scroller keyword &mdash; it also accepts an axis: <code>block</code>, <code>inline</code>, <code>x</code>, or <code>y</code>, and the two categories can be combined in either order, as in <code>scroll(nearest inline)</code>. By default the axis matches the block-flow direction, which in a normal left-to-right document is vertical &mdash; exactly why demo #1's bar fills as you scroll down. A horizontally scrolling gallery needs the inline axis explicitly, since its nearest scrollable ancestor scrolls sideways, not vertically, and <code>scroll()</code> has to be told which of the container's two scroll offsets to actually read. The progress bar in this demo is positioned absolutely inside the gallery's scroll container, so it stays visually pinned in place on screen while the cards scroll underneath it &mdash; the bar itself never moves, only its fill width, which is exactly what <code>scroll(inline)</code> is computing on every frame of the horizontal scroll.</p>

<p><strong>Best for:</strong> horizontally scrolling filmstrips, product carousels, and any layout that scrolls sideways rather than down, where a vertical <code>scroll()</code> default would silently do nothing. <strong>Tip:</strong> <code>scroll-snap-type</code> and <code>scroll()</code> combine cleanly &mdash; the snap behavior governs where the gallery settles, the timeline just keeps reading whatever the current scroll offset is at any given moment, snapped or mid-drag.</p>

<h2>7. Feature-detecting scroll-driven animation</h2>

<p>This page checks <code>@supports (animation-timeline: scroll())</code> in CSS and mirrors the identical check live in JavaScript below it. Unsupported browsers get a static, fully legible fallback instead of a broken or permanently invisible box.</p>

<iframe src="https://fwdtools.com/demos/a1/36/7.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Feature-Detecting Scroll-Driven Animation Demo by FWD Tools"></iframe>

<p><strong>The rule:</strong></p>

<pre><code class="language-css">.box { /* plain, fully visible fallback styling lives here by default */ }

@supports (animation-timeline: scroll()) {
  .box {
    animation: reveal linear both;
    animation-timeline: scroll();
    animation-range: cover 20% cover 60%;
  }
}</code></pre>

<p><code>@supports</code> checking a property/value pair is the same mechanism covered in FWD Tools' native CSS nesting guide, applied here to a genuinely load-bearing case rather than a convenience &mdash; because scroll-driven animation isn't universally supported yet, shipping it without a feature check risks a box that's permanently hidden or stuck in its <code>from</code> state on a browser that silently ignores the whole block's timeline-dependent properties while still applying whatever base styling sits outside it. The base declarations on <code>.box</code>, written outside the <code>@supports</code> block, function as the fallback automatically &mdash; if the query fails, the browser simply never reaches the nested rules, and the element keeps whatever plain, static, fully visible styling it already had. This costs nothing extra to author: the fallback is just "don't animate," which is usually already correct.</p>

<p><strong>Best for:</strong> any production use of <code>scroll()</code> or <code>view()</code> today, given the current browser support gap &mdash; treat the feature check as mandatory, not optional. <strong>Tip:</strong> <code>@supports</code> in CSS and <code>CSS.supports()</code> in JavaScript check the identical underlying capability; reach for the JS version only when the result needs to affect script logic beyond styling.</p>

<h2>8. animation-fill-mode: holding state outside the active range</h2>

<p>Scroll down slowly. The first (amber) box has no fill mode &mdash; notice it's already fully visible before you even reach it, then visibly jumps once the animation becomes active around it. The second (purple) box sets <code>animation-fill-mode: both</code> and behaves correctly.</p>

<iframe src="https://fwdtools.com/demos/a1/36/8.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="animation-fill-mode with Scroll-Driven Animation Demo by FWD Tools"></iframe>

<p><strong>The rule:</strong></p>

<pre><code class="language-css">.boxNoFill {
  animation: reveal linear;             /* no fill mode */
  animation-timeline: view();
  animation-range: entry;
}

.boxFill {
  animation: reveal linear both;        /* holds from/to state outside the range */
  animation-timeline: view();
  animation-range: entry;
}</code></pre>

<p>A scroll-driven timeline is only "active" while the element is within the range it's attached to; outside that range, the timeline is inactive and the animation stops being in effect at all. Without a fill mode, an inactive animation contributes nothing, so the element falls back to whatever its plain, unanimated CSS already says &mdash; which for an element with no other opacity or transform declared is fully opaque and untransformed, the same as the keyframes' own <code>to</code> state. The visible bug is that the element looks finished <em>before</em> it has scrolled into range at all, then briefly reinterpolates once the timeline actually activates, producing a flash instead of a clean entrance. <code>animation-fill-mode: both</code> fixes this by explicitly applying the <code>from</code> keyframe before the timeline activates and holding the <code>to</code> keyframe after it deactivates, so the element is correctly hidden ahead of its entrance and correctly settled afterward, with no gap where the plain CSS takes over instead.</p>

<p><strong>Best for:</strong> every <code>view()</code>-driven reveal without exception &mdash; this is less an optional tip and more a required companion declaration. <strong>Tip:</strong> if an element seems to ignore its <code>from</code> keyframe entirely, check for a missing fill mode before assuming the range or timeline itself is misconfigured.</p>

<h2>Common pitfalls</h2>

<ul>
<li><strong>Shipping scroll() or view() with no fallback.</strong> Native scroll-driven animation is currently Chromium-only &mdash; Chrome and Edge support it, Firefox and Safari do not as of this writing. Demo #7's <code>@supports</code> pattern isn't optional polish; without it, unsupported browsers can render a permanently hidden or stuck-mid-animation element.</li>
<li><strong>Forgetting animation-fill-mode on a view() timeline.</strong> Demo #8 is the direct proof &mdash; without <code>both</code>, an element with no other opacity/transform styling looks fully finished before it ever enters the active range, then visibly jumps once the timeline activates.</li>
<li><strong>Using scroll() with no scroller argument and assuming it means "the page."</strong> The unset default is <code>nearest</code>, not <code>root</code> &mdash; demo #2 shows how those two produce entirely different, silently different, behavior.</li>
<li><strong>Forgetting the axis on a horizontal scroller.</strong> <code>scroll()</code> defaults to the block-flow axis, which is vertical in normal documents; a sideways-scrolling gallery needs <code>scroll(inline)</code> explicitly, or the timeline reads nothing at all.</li>
<li><strong>Mismatching a named timeline's identifier.</strong> <code>scroll-timeline-name</code> and the referencing element's <code>animation-timeline</code> have to match exactly, leading <code>--</code> included &mdash; a typo produces no error, just an animation that silently never runs.</li>
</ul>

<h2>Frequently asked questions</h2>

<h3>What's the actual browser support for animation-timeline?</h3>
<p><code>scroll()</code> and <code>view()</code> timelines ship in Chrome and Edge (Chromium, version 115 onward for the unprefixed syntax). Firefox and Safari do not support them natively as of this writing, which makes demo #7's <code>@supports (animation-timeline: scroll())</code> feature-detection pattern effectively mandatory for any production use, not optional hardening.</p>

<h3>When should I use scroll() instead of view()?</h3>
<p>Use <code>scroll()</code> when the effect should track the scroll container's own position &mdash; a reading-progress bar, a horizontal gallery indicator, anything conceptually tied to "how far through the page/container has the user scrolled." Use <code>view()</code> when the effect should track one specific element's own visibility as it crosses the scrollport &mdash; a reveal-on-scroll card, a fade-in section &mdash; regardless of how far the overall page has scrolled. Demos #1 and #3 show the same-shaped bar/card driven by each, side by side.</p>

<h3>Is this a replacement for GSAP ScrollTrigger?</h3>
<p>Not a full one. It replaces ScrollTrigger's most common case &mdash; a scrub-linked or trigger-based animation with no sequencing, staggering, or velocity logic &mdash; with a zero-JavaScript, off-main-thread native mechanism, but only in Chromium browsers today. ScrollTrigger remains the cross-browser, more scriptable option; which one fits depends on the project's browser support matrix and how much scroll-scripting control the effect actually needs.</p>

<h3>Do I need a fallback for unsupported browsers, and what should it look like?</h3>
<p>Yes. The safest fallback, shown in demo #7, is simply the element's plain, static, fully visible styling with no animation at all &mdash; wrap the scroll-driven declarations in <code>@supports (animation-timeline: scroll())</code> (or <code>view()</code>) and let everything outside that block serve as the default. Avoid a JavaScript-driven fallback animation unless the effect is genuinely load-bearing for the page's usability; for most reveal and progress-bar effects, "not animated" is a perfectly acceptable degraded experience.</p>

<h3>Can scroll() and view() timelines be combined with regular CSS transitions?</h3>
<p>No &mdash; <code>animation-timeline</code> only applies to <code>@keyframes</code>-based animations set via the <code>animation</code> shorthand or longhands; CSS transitions have no equivalent timeline property and remain purely time-driven. If an effect needs to be scroll-driven, it has to be authored as a keyframe animation, even for a simple two-state change that would otherwise be a one-line <code>transition</code>.</p>

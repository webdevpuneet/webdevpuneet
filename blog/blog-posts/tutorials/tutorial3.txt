<h2>What the effect actually is</h2>

<p>Strip away the mechanical styling and the mechanism is simple to state: the board is a row of fixed-size cells, one per character. Each cell can show any glyph from a fixed character set — a leading space, then A through Z, then 0 through 9 — and knows both its <strong>current</strong> character and its <strong>target</strong> character. When a new message arrives, every cell that needs to change doesn't jump straight there. It advances one character at a time through the set, playing a small flip animation at every step, until it reaches the target. Change a cell from A to G and you'll visibly see it flap through B, C, D, E, F before landing on G — exactly like the real thing.</p>

<p>Layered on top of that per-cell mechanism is a column stagger: when a whole message changes, the cells don't all start flipping at once. Each column's animation begins a little later than the one before it, so the message updates as a ripple sweeping left to right rather than a flat, simultaneous snap.</p>

<h2>The tech stack: CSS 3D transforms and the DOM, nothing else</h2>

<p>This snippet uses nothing but the browser's built-in CSS 3D transform properties — <code>perspective</code>, <code>rotateX</code>, <code>transform-origin</code>, and <code>backface-visibility</code> — plus vanilla JavaScript driving <code>setTimeout</code> and <code>requestAnimationFrame</code>. No CDN script tags, no npm install, no build step. The entire illusion of a mechanical flap rests on rotating flat rectangles around a horizontal hinge and hiding whichever side is facing away from the viewer at any given moment.</p>

<p>If CSS 3D transforms are new territory for you, the core idea to hold onto is that <code>perspective</code> on a parent element creates a 3D viewing frustum for its children, so a <code>rotateX</code> on a child doesn't just squash it flat — it genuinely appears to tilt back into the screen, exactly like a real hinged card catching the light differently as it turns.</p>

<h2>Building it, step by step</h2>

<h3>Step 1 — The HTML and CSS: five layered pieces per cell</h3>

<p>The board itself is just a flex row of identical cells, each built from the same five-piece structure:</p>

<pre><code class="language-html">&lt;div class="flap-cell"&gt;
  &lt;div class="top"&gt;&lt;span&gt;&amp;nbsp;&lt;/span&gt;&lt;/div&gt;
  &lt;div class="bot"&gt;&lt;span&gt;&amp;nbsp;&lt;/span&gt;&lt;/div&gt;
  &lt;div class="divider"&gt;&lt;/div&gt;
  &lt;div class="flap-top-anim" style="display:none"&gt;&lt;span&gt;&amp;nbsp;&lt;/span&gt;&lt;/div&gt;
  &lt;div class="flap-bot-anim" style="display:none"&gt;&lt;span&gt;&amp;nbsp;&lt;/span&gt;&lt;/div&gt;
&lt;/div&gt;</code></pre>

<p><code>.top</code> and <code>.bot</code> are the resting state — they show the current character split across the seam and sit there whenever a cell isn't mid-flip. <code>.divider</code> is a thin line drawn across the exact middle of the cell to mimic the physical seam where a real flap card splits in two. <code>.flap-top-anim</code> and <code>.flap-bot-anim</code> are the two pieces that actually rotate during a flip, and they stay hidden (<code>display: none</code>) except for the brief moment they're animating.</p>

<p>Each cell carries <code>perspective: 300px</code>, which is what makes the child rotations that follow look like genuine 3D hinges instead of a flat squash. Both static halves clip their character with <code>overflow: hidden</code>: the <code>.top</code> half aligns its glyph to the top with <code>align-items: flex-start</code> so only the upper portion of the letter shows, and the <code>.bot</code> half aligns to the bottom with <code>align-items: flex-end</code> so only the lower portion shows. Stack them together and one full-height character reads correctly, split cleanly across the horizontal seam — exactly like a physical flap card.</p>

<h3>Step 2 — The two-beat flip: rotating away, then rotating in</h3>

<p>A real split-flap card flips in two beats: the old top leaf rotates down and away out of view, then the new bottom leaf rotates up into place. The code reproduces that with two elements rotating around opposite hinges. The animated top flap hinges at its bottom edge:</p>

<pre><code class="language-css">.flap-cell .flap-top-anim {
  transform-origin: bottom center;
  backface-visibility: hidden;
}</code></pre>

<p>It starts flat at <code>rotateX(0deg)</code> showing the <em>previous</em> character, and rotates forward to <code>rotateX(90deg)</code> — folding away from the viewer edge-on until it disappears, revealing the static <code>.top</code> underneath (which has already been silently updated to the <em>next</em> character). The animated bottom flap hinges at its top edge instead:</p>

<pre><code class="language-css">.flap-cell .flap-bot-anim {
  transform-origin: top center;
  backface-visibility: hidden;
}</code></pre>

<p>It starts folded away at <code>rotateX(-90deg)</code>, already showing the <em>next</em> character edge-on and invisible, then rotates down to <code>rotateX(0deg)</code> to snap flat into its resting position. <code>backface-visibility: hidden</code> on both pieces is what keeps the reverse side of each rotating card from flashing into view mid-turn — without it, you'd briefly see a mirrored, wrong-looking glyph as each flap passes through its edge-on position.</p>

<p>The JavaScript sequences the two halves with short <code>setTimeout</code> delays around 55ms apart, so the top folds away first and the bottom snaps in right after — that small offset between the two rotations is what reads as a single convincing mechanical clack rather than two unrelated spins.</p>

<h3>Step 3 — The double requestAnimationFrame trick</h3>

<p>Before every flip, the code has to set each animated flap to its <em>start</em> transform with transitions disabled, then re-enable the transition and apply the <em>end</em> transform a moment later — otherwise the browser has nothing to animate <em>from</em>:</p>

<pre><code class="language-javascript">animTop.style.transition = 'none';
animTop.style.transform = 'rotateX(0deg)';

requestAnimationFrame(() => {
  requestAnimationFrame(() => {
    animTop.style.transition = 'transform 0.05s ease-in';
    animTop.style.transform = 'rotateX(90deg)';
  });
});</code></pre>

<p>A single <code>requestAnimationFrame</code> isn't reliable enough here — browsers can still batch the "disable transition, set start value" write together with the very next write in the same paint, collapsing both into one and skipping the animation entirely. Nesting two calls guarantees a full frame has actually been painted with the start transform in place before the transition is turned back on and the end transform is applied. This double-rAF pattern is the standard, reliable way to trigger a CSS transition from JavaScript, and it's worth recognizing anywhere you see a snippet toggling <code>transition: none</code> before an animation.</p>

<h3>Step 4 — Stepping through the character set instead of jumping</h3>

<p>Each cell tracks a <code>current</code> index and a <code>target</code> index into a shared character set:</p>

<pre><code class="language-javascript">const CHARSET = ' ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789';</code></pre>

<p>The recursive <code>animateStep</code> function is the whole engine. It doesn't move a cell straight to its target — it advances <code>current</code> by exactly one position, using modular arithmetic to wrap back to the start of the charset if needed, plays one flip animation for that single step, and then calls itself again once the flip finishes:</p>

<pre><code class="language-javascript">function animateStep(cellObj) {
  if (cellObj.current === cellObj.target) {
    cellObj.animating = false;
    return;
  }
  cellObj.animating = true;
  cellObj.current = (cellObj.current + 1) % CHARSET.length;
  // ...play one flip from the old character to the new one...
  setTimeout(() => animateStep(cellObj), 10);
}</code></pre>

<p>The recursion only stops once <code>current</code> catches up to <code>target</code>. That's the entire reason a cell changing from A to G visibly flaps through B, C, D, E, F on the way — it's not a scripted sequence, it's just this one function repeatedly asking "am I there yet?" and taking one more step if not.</p>

<h3>Step 5 — Setting a message: eight cells, staggered</h3>

<p>The board is a fixed number of cells (eight in this build). <code>displayMessage</code> pads or trims whatever text comes in to exactly that length:</p>

<pre><code class="language-javascript">function padMsg(msg) {
  return msg.toUpperCase().padEnd(NUM_CELLS, ' ').slice(0, NUM_CELLS);
}</code></pre>

<p>Then for every cell it looks up the target character's index in <code>CHARSET</code> (falling back to a space for anything outside the supported set) and kicks off <code>animateStep</code> — but not all at once. Each cell's start is delayed by <code>i * 40</code> milliseconds, where <code>i</code> is its column position:</p>

<pre><code class="language-javascript">padded.split('').forEach((ch, i) => {
  const idx = CHARSET.indexOf(ch) === -1 ? 0 : CHARSET.indexOf(ch);
  cells[i].target = idx;
  if (!cells[i].animating) {
    setTimeout(() => animateStep(cells[i]), i * 40);
  }
});</code></pre>

<p>That single <code>i * 40</code> offset is what produces the left-to-right ripple across the whole board — without it, every cell would start flipping in the exact same instant, and the board would lose the sense of a mechanical wave passing over it. A per-cell <code>animating</code> flag guards against a second message arriving mid-flip from starting a duplicate animation chain on the same cell.</p>

<h3>Step 6 — Keeping the board alive: presets and auto-cycling</h3>

<p>A row of preset buttons is generated from a small array of sample messages, each wired to call <code>displayMessage</code> on click. A text input lets visitors type up to eight characters of their own, committing on the Set button or the Enter key. And a <code>setInterval</code> quietly rotates through the presets every few seconds on its own, so the board is never sitting frozen — much like a real departures sign that's always mid-update for something.</p>

<h2>Customizing it for your own project</h2>

<p>A few knobs worth knowing about if you're adapting this:</p>

<ul>
<li><strong>Character set</strong> — add symbols, punctuation, or lowercase letters to <code>CHARSET</code>. The cycling logic uses <code>indexOf</code> and modular arithmetic, so it adapts to any length automatically, though a longer set means more intermediate flips for characters far apart in the string.</li>
<li><strong>Flip speed</strong> — the transition durations on the animated flaps (around 0.05s each) and the 55ms <code>setTimeout</code> gap between the top and bottom beats together control how snappy or leisurely each individual flip feels.</li>
<li><strong>Ripple timing</strong> — the <code>i * 40</code> per-column stagger controls how pronounced the left-to-right wave looks; raise it for a slower, more deliberate sweep, or drop it toward zero for a near-simultaneous update.</li>
<li><strong>Board size</strong> — <code>NUM_CELLS</code> controls how many characters the board holds; the cell-creation loop and padding logic both scale automatically.</li>
</ul>

<h2>Using it in React, Vue, or Angular</h2>

<p>The one rule that matters when porting this into a component framework is: create the cells and kick off any initial cycling inside a mount lifecycle hook — <code>useEffect</code> in React, <code>onMounted</code> in Vue, <code>ngAfterViewInit</code> in Angular — never at module or render time, since the DOM elements the animation manipulates directly need to exist first. Keep each cell's <code>current</code>/<code>target</code>/<code>animating</code> state in a ref or plain array rather than component state, since re-rendering the whole board on every single character flip would fight the recursive <code>setTimeout</code> chain and stutter the animation. On unmount, clear any active <code>setInterval</code> auto-cycling and let in-flight <code>setTimeout</code> chains run out naturally rather than trying to cancel mid-flip. When the message is passed in as a prop, call the same <code>displayMessage</code>-equivalent logic whenever it changes, exactly like the Set button does in the vanilla version.</p>

<h2>What the effect actually is</h2>

<p>A Lottie is a vector animation exported as JSON — most often from After Effects via the Bodymovin plugin, though you can author one by hand too. Normally you load it and it plays on a timer: press go, and it runs at its designed frame rate from start to finish. <strong>Scrubbing</strong> throws that timer away. Instead of "play," the animation is told to sit frozen on a single specific frame, and <em>which</em> frame is decided entirely by how far the visitor has scrolled. Scroll to 25% of the way through a section and the animation jumps to 25% of its frames; scroll to 60% and it's on frame 60%; scroll back up and it walks backward through its own frames. The animation becomes a slider, and the scrollbar is the handle.</p>

<p>Everything else in this snippet is built on that one idea. The visible result — a ring that draws on and a checkmark that strokes in — is just what <em>this</em> particular Lottie happens to contain. Swap the JSON for any other Lottie and the exact same scrubbing machinery drives it, whether that's a character walking, a logo assembling, or a box unfolding.</p>

<h2>The tech stack: lottie-web and GSAP ScrollTrigger</h2>

<p>This snippet uses exactly two libraries, both from a CDN — no bundler, no build step. <a href="https://fwdtools.com/ui-snippets/scroll/"><strong>lottie-web</strong></a> is the official player that turns Lottie JSON into an animated SVG (or canvas) and exposes the API for seeking to a specific frame. <strong>GSAP</strong> with its <strong>ScrollTrigger</strong> plugin handles the scroll side: pinning a section in place and producing a smooth 0-to-1 progress value as the visitor scrolls through it. The whole effect is the marriage of those two — ScrollTrigger says "you're 40% through," and lottie-web is told "then show me frame 40%."</p>

<p>If GSAP ScrollTrigger is new to you, the one concept to hold onto is the <strong>scrub</strong>: rather than firing an animation once when an element enters the viewport, a scrubbed ScrollTrigger ties an animation's progress directly to scroll position, so it plays forward as you scroll down and backward as you scroll up. The same scrubbing idea powers the <a href="https://fwdtools.com/ui-snippets/scroll-typewriter/">scroll typewriter</a> snippet — here we point it at a Lottie's frame instead of typed characters.</p>

<h2>Building it, step by step</h2>

<h3>Step 1 — The HTML and CSS: a pinned stage with a mount point</h3>

<p>The markup is deliberately minimal: a full-height section that will get pinned, containing a single empty <code>&lt;div&gt;</code> for lottie-web to render into, plus a caption overlay and a small progress read-out.</p>

<pre><code class="language-html">&lt;section class="lot-stage" id="lotStage"&gt;
  &lt;div class="lot-intro-overlay"&gt;&lt;p&gt;Scroll &darr; to play the Lottie&lt;/p&gt;&lt;/div&gt;
  &lt;div class="lot-wrap"&gt;&lt;div class="lot-canvas" id="lotMount"&gt;&lt;/div&gt;&lt;/div&gt;
  &lt;div class="lot-hud"&gt;&lt;span id="lotPct"&gt;0&lt;/span&gt;% complete&lt;/div&gt;
&lt;/section&gt;
&lt;section class="lot-bottom"&gt;&lt;p&gt;Animation complete &mdash; scroll up to rewind it.&lt;/p&gt;&lt;/section&gt;</code></pre>

<p><code>#lotMount</code> is the only element that matters to the animation — lottie-web will inject an <code>&lt;svg&gt;</code> into it. It's given a fixed size in CSS (around 340&times;340) so the vector has a box to scale into. The <code>.lot-stage</code> is <code>height: 100vh</code> and <code>position: relative</code> so the caption overlay can sit centered over the animation, and a second <code>.lot-bottom</code> section below it gives the page something to scroll into after the pinned stage releases.</p>

<h3>Step 2 — Lottie is just JSON: load it inline with animationData</h3>

<p>Most Lottie tutorials load the animation from a URL, like <code>lottie.loadAnimation({ path: 'anim.json' })</code>. That works, but it means an extra network request and a file you have to host somewhere. This snippet takes the other route: it passes the animation directly as an <code>animationData</code> object, so the JSON ships inside the component and there's nothing to fetch and nothing that can 404.</p>

<pre><code class="language-javascript">const animationData = {
  v: '5.7.4', fr: 60, ip: 0, op: 120, w: 400, h: 400, nm: 'scroll-ring', ddd: 0, assets: [],
  layers: [ /* a track ring, a progress ring, and a checkmark */ ]
};

const anim = lottie.loadAnimation({
  container: document.getElementById('lotMount'),
  renderer: 'svg',
  loop: false,
  autoplay: false,   // &larr; the important part, see Step 3
  animationData,
});</code></pre>

<p>Those top-level fields are the Lottie schema: <code>fr</code> is the frame rate, <code>ip</code> and <code>op</code> are the in and out points in frames (so this animation is 120 frames long), <code>w</code>/<code>h</code> are its dimensions, and <code>layers</code> is the array of shapes. The best part of inlining it: swapping in your own animation is a one-line change. Delete the <code>animationData</code> object and pass <code>path: 'your-animation.json'</code> instead — every other line in this tutorial stays identical, because the player's API is the same either way.</p>

<h3>Step 3 — autoplay:false and goToAndStop: making it scrubbable</h3>

<p>The single most important option above is <code>autoplay: false</code>. A normal Lottie starts running on its own clock the instant it loads; here we never want that internal timer to tick, because scroll position — not elapsed time — decides which frame is visible. With autoplay disabled and <code>loop: false</code>, the animation sits frozen at frame 0 until we explicitly move it.</p>

<p>Moving it is one method call:</p>

<pre><code class="language-javascript">anim.goToAndStop(frame, true);</code></pre>

<p>That second argument, <code>true</code>, tells lottie-web the value is a <strong>frame number</strong> rather than a time in milliseconds, and <code>goToAndStop</code> renders that single still frame without starting playback. To turn a 0-to-1 scroll progress into a frame, you multiply by the total number of frames:</p>

<pre><code class="language-javascript">const p = 0.4;                              // 40% scrolled
anim.goToAndStop(p * (anim.totalFrames - 1), true);   // show frame ~48 of 120</code></pre>

<p>Because lottie-web interpolates between keyframes, a fractional frame like <code>47.6</code> renders smoothly — so the ring grows continuously as you scroll rather than snapping between whole frames.</p>

<h3>Step 4 — Driving one scrubbed value with ScrollTrigger</h3>

<p>Rather than reading the raw scroll offset by hand, the snippet lets GSAP produce a clean 0-to-1 value. It tweens a single plain number — <code>state.p</code> — from 0 to 1, tied to a ScrollTrigger that pins the stage and scrubs over a range several viewport-heights tall:</p>

<pre><code class="language-javascript">gsap.registerPlugin(ScrollTrigger);

const state = { p: 0 };
gsap.to(state, {
  p: 1,
  ease: 'none',
  scrollTrigger: {
    trigger: '#lotStage',
    start: 'top top',
    end: '+=400%',   // the pinned scroll distance
    scrub: 0.5,      // smooth the value toward the scroll position
    pin: true,
  },
});</code></pre>

<p>Then a plain <code>requestAnimationFrame</code> loop reads <code>state.p</code> every frame and seeks the Lottie to the matching frame — independent of the scroll callback, exactly like the pattern used across the other scroll snippets:</p>

<pre><code class="language-javascript">function tick() {
  requestAnimationFrame(tick);
  if (!total) return;                        // total = anim.totalFrames once loaded
  const p = Math.max(0, Math.min(1, state.p));
  anim.goToAndStop(p * (total - 1), true);
  document.getElementById('lotPct').textContent = Math.round(p * 100);
}
tick();</code></pre>

<p>Deriving the frame from one normalized value each frame is what makes the effect <strong>fully reversible</strong> for free: scrolling up simply produces smaller values of <code>state.p</code>, so <code>goToAndStop</code> seeks earlier frames and the animation plays backward — the ring un-draws and the checkmark retracts — with no extra reverse-playback code. The numeric <code>scrub: 0.5</code> adds about half a second of easing so the animation glides toward the scroll position instead of snapping frame-perfectly to every noisy wheel tick.</p>

<h3>Step 5 — The draw effect: Lottie trim paths</h3>

<p>The ring and checkmark don't fade in — they <em>stroke on</em>, like a pen drawing a line. That's a Lottie <strong>trim path</strong>, shape type <code>tm</code>, which renders only a portion of a stroked path from a start percentage to an end percentage. Animating the trim's <em>end</em> from 0 to 100 across the timeline makes the stroke appear to draw itself. Here's the progress ring: an ellipse, a trim whose end is keyframed 0&rarr;100, and a stroke, grouped together:</p>

<pre><code class="language-javascript">shapes: [{
  ty: 'gr',
  it: [
    { ty: 'el', s: { a: 0, k: [200, 200] }, p: { a: 0, k: [0, 0] } },   // ellipse
    { ty: 'tm', s: { a: 0, k: 0 },                                       // trim: start 0
      e: { a: 1, k: [ /* end keyframes 0 -> 100 */ ] }, o: { a: 0, k: 0 }, m: 1 },
    { ty: 'st', c: { a: 0, k: [0.45, 0.53, 0.98, 1] }, w: { a: 0, k: 16 } }, // stroke
    { ty: 'tr' }                                                         // group transform
  ]
}]</code></pre>

<p>A second, static ring with no trim sits behind it at low opacity as the "track," so the circle's full path is always visible — exactly like a circular progress indicator. The checkmark is the same idea: a small open path whose trim end is keyframed to draw in over the last third of the timeline, so it only appears once the ring is nearly complete. Because trim is part of the JSON, the drawing behavior travels with the animation wherever the player runs — it's the Lottie equivalent of animating <code>stroke-dashoffset</code> on an SVG, but authored once inside the file.</p>

<h3>Step 6 — The keyframe gotcha that silently breaks everything</h3>

<p>This is the one detail worth burning into memory, because it produces a blank animation with no error message. When you hand-author (or tweak) a keyframed Lottie property, <strong>each animated keyframe must carry its easing tangents</strong> — the <code>i</code> (in) and <code>o</code> (out) bezier handles. Leave them off and lottie-web treats the keyframe as a <em>hold</em> keyframe: it never interpolates, so the value stays pinned at the first keyframe forever. For a trim animating 0&rarr;100, that means the end stays at 0, the trimmed stroke has zero length, and the ring renders as an empty path — even though the frame is advancing correctly.</p>

<p>The fix is to give every animated keyframe linear tangents. Control points at <code>(0.5, 0.5)</code> describe a straight diagonal — i.e. true linear interpolation:</p>

<pre><code class="language-javascript">e: { a: 1, k: [
  { i: { x: [0.5], y: [0.5] }, o: { x: [0.5], y: [0.5] }, t: 0,   s: [0]   },
  { t: 120, s: [100] }
] }</code></pre>

<p>Symptom to recognize: if a Lottie's <code>currentFrame</code> is clearly advancing but a trimmed or animated shape isn't changing, suspect missing <code>i</code>/<code>o</code> tangents before anything else. Bodymovin always exports them, which is why the problem only tends to show up when you write or edit the JSON by hand.</p>

<h3>Step 7 — Fading the caption as the animation begins</h3>

<p>One small touch keeps the intro caption from sitting on top of the finished animation. The same <code>tick</code> loop that seeks the frame also fades the overlay out once scrolling starts and back in when you return to the top:</p>

<pre><code class="language-javascript">intro.style.opacity = p &gt; 0.02 ? '0' : '1';</code></pre>

<p>Because it's driven by the same scrubbed <code>p</code>, it reverses automatically like everything else — scroll back to the very top and the "Scroll to play" prompt fades right back in.</p>

<h2>Customizing it for your own project</h2>

<p>A few knobs worth knowing about if you're adapting this:</p>

<ul>
<li><strong>Your own animation</strong> — the whole point of the inline JSON is that it's swappable. Replace <code>animationData</code> with <code>path: 'your-animation.json'</code> to drive any exported Lottie with the exact same scroll logic.</li>
<li><strong>Scroll length</strong> — the ScrollTrigger <code>end: '+=400%'</code> controls how much scrolling maps to the full animation; raise it for a longer, slower playback or lower it for a quick one.</li>
<li><strong>Smoothness</strong> — the numeric <code>scrub</code> value (0.5) sets how much the animation eases toward the scroll position; drop it toward 0 for a tighter, more immediate response, or raise it for a more floaty glide.</li>
<li><strong>Renderer</strong> — <code>renderer: 'svg'</code> keeps the vector razor-sharp and easy to add a CSS glow to; for very heavy animations you can switch to <code>'canvas'</code> for better raw performance at the cost of crispness.</li>
</ul>

<h2>Using it in React, Vue, or Angular</h2>

<p>The one rule that matters when porting this into a component framework is: create the animation and register the ScrollTrigger inside a mount lifecycle hook — <code>useEffect</code> in React, <code>onMounted</code> in Vue, <code>ngAfterViewInit</code> in Angular — against a ref to the mount element, never at render or module time, since lottie-web needs a real DOM node to draw into. Keep the <code>anim</code> instance and the scrubbed value in refs rather than component state, so a re-render never tears down the running animation. Most importantly, clean up on unmount: call <code>anim.destroy()</code> to release the SVG and the player, and kill the ScrollTrigger instance (or revert a <code>gsap.context</code>) so the pin and scroll listener don't leak. The official <code>lottie-react</code> wrapper works too, but calling the raw player as shown here keeps the frame-seeking logic fully in your control, which is exactly what you want for scrubbing.</p>

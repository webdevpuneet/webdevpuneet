<!-- wp:heading -->
<h2 class="wp-block-heading">What the effect actually is</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Strip away the visual polish and the mechanism is simple to state: a word is drawn once, invisibly, purely to find out which pixels belong to its letters. Every one of those pixels becomes a target point for a particle. Thousands of particles then start at random positions and get nudged toward their assigned target every frame, a little more each time, until they settle into the shape of the word. Click the canvas and every particle instead gets a random outward push plus gravity, so the word disintegrates into a cloud that arcs and falls like a firework &mdash; then, a moment later, the same springs pull everything back home.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>Nothing about this requires knowing where letters "are" in any geometric sense &mdash; no font-outline parsing, no bezier math. The browser's own text renderer draws the glyphs; the code just asks the canvas which pixels ended up lit.</p>
<!-- /wp:paragraph -->

<h2 class="wp-block-heading">The tech stack: just the Canvas 2D API</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>This snippet uses nothing but the browser's built-in <a href="https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API" target="_blank" rel="noopener">Canvas 2D API</a> and <code>requestAnimationFrame</code> &mdash; no CDN script tags, no npm install, no build step. The whole trick rests on two Canvas methods most people only use for basic drawing: <code>fillText</code>, to render the word, and <code>getImageData</code>, to read the pixels back out as raw numbers. Everything else &mdash; the physics, the state machine, the rendering &mdash; is arithmetic run inside a plain animation loop.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>If Canvas 2D is new territory for you, the core idea to hold onto is that a canvas is really just a grid of pixel bytes you can both write to (<code>fillRect</code>, <code>fillText</code>, <code>arc</code>, and so on) and read back from (<code>getImageData</code>). Almost every "sample an image and do something with it" effect on the web &mdash; this one included &mdash; is built on that read-back capability.</p>
<!-- /wp:paragraph -->

<h2 class="wp-block-heading">Building it, step by step</h2>
<!-- /wp:heading -->

<!-- wp:heading {"level":3} -->
<h3 class="wp-block-heading">Step 1 &mdash; The HTML and CSS: a canvas, a text input, and two buttons</h3>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>The markup is deliberately thin &mdash; a full-bleed <code>&lt;canvas&gt;</code> plus a small control bar underneath it:</p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>&lt;div class="app"&gt;
  &lt;canvas id="canvas"&gt;&lt;/canvas&gt;
  &lt;div class="controls"&gt;
    &lt;input type="text" id="textInput" value="HELLO" maxlength="10" placeholder="Enter text..." spellcheck="false"&gt;
    &lt;button id="applyBtn"&gt;Apply&lt;/button&gt;
    &lt;button id="toggleBtn"&gt;Explode&lt;/button&gt;
    &lt;span class="hint"&gt;Click canvas to toggle&lt;/span&gt;
  &lt;/div&gt;
&lt;/div&gt;</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>The canvas is set to <code>flex: 1</code> inside a column flex container so it fills all the space above the control bar, and its actual pixel dimensions are set in JavaScript from <code>offsetWidth</code>/<code>offsetHeight</code> rather than CSS alone &mdash; a canvas element's drawing buffer and its displayed size are two separate things, and only setting the <code>width</code>/<code>height</code> attributes (not just CSS) gives you a crisp, correctly-scaled drawing surface.</p>
<!-- /wp:paragraph -->

<!-- wp:heading {"level":3} -->
<h3 class="wp-block-heading">Step 2 &mdash; Sampling the word into target points</h3>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>This is the idea the whole effect is built on, and it's worth sitting with. The particles need to know <em>where</em> the letters are, in pixel coordinates. To find out, the code draws the word onto a hidden, off-screen canvas &mdash; one that's never appended to the page &mdash; with a large bold font, then calls <code>getImageData</code> to read the entire pixel buffer back as numbers:</p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>const off = document.createElement('canvas');
const FONT_SIZE = Math.min(120, W * 0.25);
off.width = W; off.height = H;
const oc = off.getContext('2d');
oc.fillStyle = '#fff';
oc.font = `bold ${FONT_SIZE}px Arial, sans-serif`;
oc.textAlign = 'center';
oc.textBaseline = 'middle';
oc.fillText(text.toUpperCase(), W/2, H/2);

const imageData = oc.getImageData(0, 0, W, H);
const data = imageData.data;</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p><code>getImageData</code> returns a flat <code>Uint8ClampedArray</code> with four bytes per pixel &mdash; red, green, blue, alpha, in that order, row by row. For a canvas that's never been shown to a user, that's fine; it exists purely as scratch space for this one calculation.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>The code then walks that array on a <strong>stride</strong> &mdash; stepping several pixels at a time in both x and y, rather than checking literally every pixel &mdash; and for each sampled coordinate checks the alpha byte:</p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>for (let y = 0; y &lt; H; y += stride) {
  for (let x = 0; x &lt; W; x += stride) {
    const idx = (y * W + x) * 4;
    if (data[idx + 3] &gt; 128) {
      particles.push({ tx: x, ty: y, x: Math.random() * W, y: Math.random() * H, vx: 0, vy: 0, hue: (x / W) * 360, alpha: 1 });
    }
  }
}</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>An alpha value above 128 means that pixel is solidly part of a letter, not background or an anti-aliased edge &mdash; so it becomes a particle's <strong>target</strong> position <code>(tx, ty)</code>. The particle itself starts somewhere random on screen, with zero velocity, ready to be pulled toward that target once the animation loop starts. The stride is the effect's main density-vs-performance dial: a smaller stride samples more pixels, giving denser, crisper letters at a higher particle count and cost; a larger stride is sparser and cheaper. A stride of a few pixels comfortably produces a few thousand particles for a clean, readable word.</p>
<!-- /wp:paragraph -->

<!-- wp:heading {"level":3} -->
<h3 class="wp-block-heading">Step 3 &mdash; The spring: making particles ease into place</h3>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Every particle carries a current position <code>(x, y)</code>, a velocity <code>(vx, vy)</code>, and its target <code>(tx, ty)</code>. Each frame, in the <code>FORM</code> state, it runs the same four lines:</p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>p.vx += (p.tx - p.x) * 0.08;
p.vy += (p.ty - p.y) * 0.08;
p.vx *= 0.85;
p.vy *= 0.85;
p.x += p.vx;
p.y += p.vy;</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>This is a damped spring, and it's one of the most useful four-liners in animation programming &mdash; worth understanding well past this one effect. The first two lines are the "spring" half: velocity gains a push proportional to how far the particle still is from its target, so a particle that's far away accelerates hard, like a stretched rubber band, while a particle that's nearly there barely gets nudged. Left alone, that would make every particle overshoot and oscillate forever, like a mass on an ideal spring with no friction.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>The next two lines are the "damping" half: velocity is multiplied by a factor just under 1 every frame, bleeding off a little energy each time. That's the friction. Tune the spring constant (<code>0.08</code> here) and the damping factor (<code>0.85</code>) together and you control the whole feel of the motion &mdash; a stiffer spring with less damping snaps into place with a visible overshoot and wobble; a softer spring with more damping eases in smoothly with no bounce at all. Because every particle runs this same tiny simulation completely independently of every other one, a cloud of thousands of them organically resolves into readable text with no coordination logic required anywhere.</p>
<!-- /wp:paragraph -->

<!-- wp:heading {"level":3} -->
<h3 class="wp-block-heading">Step 4 &mdash; The state machine: FORM and EXPLODE</h3>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>The whole effect is driven by one variable, <code>state</code>, that's either <code>'FORM'</code> or <code>'EXPLODE'</code>. Clicking the canvas (or the toggle button) flips it:</p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>function explode() {
  state = 'EXPLODE';
  particles.forEach(p =&gt; {
    p.vx = (Math.random() - 0.5) * 16;
    p.vy = -5 - Math.random() * 10;
    p.alpha = 1;
  });
}</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>Every particle is handed a random horizontal velocity and an upward-biased vertical velocity &mdash; enough to make the whole word visibly burst outward and up rather than just drifting apart. From there, the update loop for the <code>EXPLODE</code> state applies simple projectile motion:</p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>particles.forEach(p =&gt; {
  p.vy += 0.15;       // gravity
  p.x += p.vx;
  p.y += p.vy;
  p.alpha -= 0.008;   // fade out
});
particles = particles.filter(p =&gt; p.alpha &gt; 0 &amp;&amp; p.y &lt; H + 50);</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>A constant downward acceleration added to <code>vy</code> every frame is gravity &mdash; no different from the physics you'd write for a simple platformer. Particles fade as they fall and get pruned once they're transparent or have dropped off the bottom of the canvas, so the array doesn't grow unbounded. When <code>reform()</code> is called, every particle is simply thrown back to a random position with zero velocity and the state flips back to <code>FORM</code> &mdash; at which point the exact same spring code from Step 3 takes back over and pulls everything home. The explosion and the reassembly are two completely different pieces of motion logic, but they operate on the exact same particle array, which is what makes toggling between them instant and seamless.</p>
<!-- /wp:paragraph -->

<!-- wp:heading {"level":3} -->
<h3 class="wp-block-heading">Step 5 &mdash; Rendering thousands of particles without dropping frames</h3>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>The draw step runs once per frame, after the physics update:</p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>ctx.fillStyle = 'rgba(13,13,26,0.25)';
ctx.fillRect(0, 0, W, H);

particles.forEach(p =&gt; {
  ctx.globalAlpha = Math.max(0, p.alpha);
  ctx.fillStyle = `hsl(${p.hue}, 80%, 65%)`;
  ctx.fillRect(p.x, p.y, 2, 2);
});
ctx.globalAlpha = 1;</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>Two choices here matter for performance. First, instead of clearing the canvas outright each frame, it paints a semi-transparent rectangle over the whole thing. Because that rectangle doesn't fully erase what's underneath, every particle leaves a very short motion trail behind it before it fades to background &mdash; a cheap way to make fast-moving particles read as smoother streaks rather than flickering dots, for the cost of one <code>fillRect</code> call.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>Second, each particle is drawn with <code>fillRect(x, y, 2, 2)</code> &mdash; a tiny filled square &mdash; rather than the more "correct-looking" <code>arc()</code> circle. Building a circular path and filling it is meaningfully more expensive than filling a rectangle, and at a small enough size the visual difference between a 2px square and a 2px circle is imperceptible. With a few thousand particles updating and drawing every frame, that one substitution is often the difference between a smooth 60fps and a stutter.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>Color comes from each particle's horizontal position at the moment it was sampled &mdash; <code>hue: (x / W) * 360</code> &mdash; mapped straight into an HSL color string. Because that hue is assigned once per particle and never changes, the assembled word displays a smooth left-to-right rainbow gradient that rides along with the particles even while they're mid-flight during an explosion.</p>
<!-- /wp:paragraph -->

<!-- wp:heading {"level":3} -->
<h3 class="wp-block-heading">Step 6 &mdash; Changing the word without a hard cut</h3>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Typing a new word into the input and pressing Apply doesn't restart the effect from scratch &mdash; it re-samples the offscreen canvas with the new text and rebuilds the particle array, but each particle still just gets a fresh <code>(tx, ty)</code> target and resumes the same spring behavior from Step 3. Because the particles' actual on-screen positions aren't reset, the transition from one word to the next plays out as a smooth animated morph &mdash; the old shape's cloud of dots simply gets reassigned new destinations and drifts into the new word &mdash; rather than a jarring cut from one static word to another.</p>
<!-- /wp:paragraph -->

<h2 class="wp-block-heading">Customizing it for your own project</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>A few knobs worth knowing about if you're adapting this:</p>
<!-- /wp:paragraph -->

<!-- wp:list -->
<ul class="wp-block-list">
<!-- wp:list-item -->
<li><strong>Density vs. performance</strong> &mdash; lower the sampling stride for denser, crisper text at a higher particle count and CPU cost, or raise it for a sparser, faster effect. The particle count always follows the letters' pixel area automatically.</li>
<!-- /wp:list-item -->
<!-- wp:list-item -->
<li><strong>Motion feel</strong> &mdash; raise the spring constant or lower the damping factor for a snappier assembly with visible overshoot; do the opposite for a slower, floatier ease-in with no bounce at all.</li>
<!-- /wp:list-item -->
<!-- wp:list-item -->
<li><strong>Explosion strength</strong> &mdash; the random velocity ranges in <code>explode()</code> and the gravity constant in the update loop control how violently the word bursts apart and how quickly it falls; scale them together to keep the arc looking natural.</li>
<!-- /wp:list-item -->
<!-- wp:list-item -->
<li><strong>Color scheme</strong> &mdash; the hue is derived from horizontal position, but it could just as easily be a fixed brand color, mapped from vertical position instead, or randomized per particle for a more chaotic palette.</li>
<!-- /wp:list-item -->
</ul>

<h2 class="wp-block-heading">Using it in React, Vue, or Angular</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>The one rule that matters when porting a canvas animation loop into a component framework is: set up the canvas, sample the text, and start <code>requestAnimationFrame</code> inside a mount lifecycle hook &mdash; <code>useEffect</code> in React, <code>onMounted</code> in Vue, <code>ngAfterViewInit</code> in Angular &mdash; never at module or render time, since the canvas element and its dimensions need to exist first. Store the particle array and animation frame ID in a ref (React) or a component field (Vue/Angular) rather than component state, since re-rendering per particle, per frame, would fight the animation loop and tank performance. On unmount, call <code>cancelAnimationFrame</code> with the stored ID so the loop doesn't keep running against a canvas that's no longer in the DOM. When the displayed word is passed in as a prop, re-run the sampling step whenever it changes, exactly like the Apply button does in the vanilla version.</p>

<h2 class="wp-block-heading">Final thought</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>What makes this snippet worth studying isn't the particle text effect itself &mdash; it's the underlying pattern: <strong>decouple the "where" from the "how."</strong> An offscreen canvas plus <code>getImageData</code> answers where the text is, producing nothing more than a flat list of target points. A damped spring answers how anything gets from A to B, and it has no idea it's moving toward letters &mdash; it would just as happily pull particles toward a logo, a photo's silhouette, or a mouse cursor. Once that split clicks, the same two ingredients &mdash; pixel sampling for targets, spring-and-damping for motion &mdash; turn into image reveals, morphing shapes, and cursor-following swarms, all built from the same handful of lines.</p>

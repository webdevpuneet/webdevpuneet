<h1>10 Scroll Animations Built on the New CSS animation-timeline API (8 With Zero JavaScript)</h1>

<p>For as long as scroll-driven animation has existed on the web, it has meant JavaScript: a <code>scroll</code> event listener, a <code>getBoundingClientRect()</code> call, and — if you wanted it smooth — a <code>requestAnimationFrame</code> loop tying the two together. GSAP's ScrollTrigger made that pattern pleasant to write, but it was still fundamentally the browser's main thread doing math on every scroll tick. The CSS Scroll-Driven Animations API changes the deal entirely: <code>animation-timeline: scroll()</code> and <code>animation-timeline: view()</code> let a <code>@keyframes</code> animation's 0%–100% playback position bind directly to scroll position instead of to a duration in seconds — computed by the browser's compositor, off the main thread, with no listener anywhere in the JavaScript.</p>

<p>Eight of the ten snippets below use exactly that — genuinely zero JavaScript driving the animation, verified by reading the actual <code>js</code> field of each one (it only logs a feature-support check, nothing more). The other two are included deliberately as an honest counterpoint: real numeric counting and per-element staggered reveals still need <code>IntersectionObserver</code> and <code>requestAnimationFrame</code> today, and knowing which category a given effect falls into is most of the skill here. Every one is a <strong>live, interactive preview</strong> you can try right here in the article, and each exports to React, Vue, Angular or Tailwind in one click from its snippet page.</p>

<h2>What these ten get right</h2>

<ul>
<li><strong>The timeline doesn't care what it's driving.</strong> <code>animation-timeline: scroll(root)</code> shows up in this batch animating an SVG <code>stroke-dashoffset</code>, a <code>filter: hue-rotate()</code>, a <code>transform: scaleX()</code>, and a CSS <code>counter()</code> — the same primitive, four completely different properties, because a scroll timeline is just a 0%–100% progress value with no opinion about what consumes it.</li>
<li><strong>A timeline's source and its consumer don't have to be the same element.</strong> The heading-underline snippet puts <code>view-timeline-name: --para-read</code> on a paragraph and <code>animation-timeline: --para-read</code> on a completely different underline bar beneath it — so the underline fills based on how far the reader has scrolled through the paragraph's own text, not its own position.</li>
<li><strong><code>steps()</code> beats <code>linear</code> the moment the value is discrete.</strong> The section counter animates a CSS <code>counter()</code> — a whole number that cannot interpolate fractionally — using <code>animation: steps(4)</code> rather than <code>linear</code>, so the displayed number always lands on a clean integer instead of a nonsensical blended one.</li>
<li><strong><code>view-timeline-axis</code> follows the scroll direction the layout actually uses.</strong> Vertical page layouts use the default <code>block</code> axis; the horizontally-scrolling saturation gallery and snap carousel both switch to <code>view-timeline-axis: inline</code> so each frame's timeline tracks its own left-right position instead of a vertical one that would never change.</li>
<li><strong>An <code>@supports not (...)</code> fallback is not optional.</strong> Every native-CSS snippet in this batch wraps its animation in <code>@supports not (animation-timeline: scroll())</code> or the <code>view()</code> equivalent, resetting to a sane static state — a full ring, a flat card, a mid-hue background — because Firefox and Safari support is still landing, and a browser that ignores the property entirely would otherwise leave the animated value stuck at its starting keyframe.</li>
</ul>

<h2>2. 3D Card Rotate on Scroll (view-timeline)</h2>

<p>Each card rotates in on its Y-axis and settles flat as it enters the viewport, then rotates back out as it leaves — a per-card native timeline, not a shared one.</p>

<iframe src="https://fwdtools.com/ui-snippets/view-timeline-card-rotate-3d/embed/" style="width:100%;height:640px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="3D Card Rotate on Scroll (view-timeline) — Free HTML CSS JS Snippet by FWD Tools"></iframe>

<p><strong>How it works:</strong> every card declares its own <code>view-timeline-name: --card-in</code> and <code>view-timeline-axis: block</code>. <h2>4. Sticky Section Counter (scroll-timeline)</h2>

<p><strong>How it works:</strong> a pseudo-element's <code>content: counter(sec-count, decimal-leading-zero)</code> displays a native CSS counter, and a scroll-bound animation on <code>counter-increment</code> steps that counter upward using <code>animation: steps(4)</code> rather than <code>linear</code> — <code>linear</code> would blend between counter values in a way that makes no sense for a whole number, since CSS counters don't interpolate fractionally, while <code>steps(4)</code> forces four clean discrete jumps. <p><strong>Best for:</strong> editorial sites and documentation pages with a fixed, known number of sections. <strong>Tip:</strong> update <code>counter-reset</code> and the number of increment stops in the keyframes to match your real section count.</p>

<h2>9. Count-Up Stats on Scroll (IntersectionObserver)</h2>

<p>Stat cards whose numbers count up from zero exactly once when scrolled into view — the deliberate JS counterpoint in this batch, because real numeric interpolation still needs it.</p>

<iframe src="https://fwdtools.com/ui-snippets/scroll-reveal-counter-stats/embed/" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Count-Up Stats on Scroll (IntersectionObserver) — Free HTML CSS JS Snippet by FWD Tools"></iframe>

<p><strong>How it works:</strong> this is included specifically because it's the effect this batch's native-CSS techniques genuinely can't reach yet — plain CSS has no way to smoothly interpolate an arbitrary number into readable text without registering a custom <code>@property</code>, which is why the section counter above used discrete <code>steps()</code> instead. Here, a single shared <code>IntersectionObserver</code> watches every stat number via one <code>querySelectorAll</code> loop — far cheaper than one observer per element — and once a number enters view, <code>requestAnimationFrame</code> drives a 1400ms count from zero to its target, eased with <code>1 - Math.pow(1 - progress, 3)</code> so it decelerates naturally into its final value instead of stopping mechanically. Before animating anything, it checks <code>prefers-reduced-motion</code> and, if set, jumps straight to the final number with no animation loop at all.</p>

<p><strong>Best for:</strong> pricing pages, about pages, and case-study sections with a handful of headline metrics worth a moment of emphasis. <strong>Tip:</strong> this is exactly the kind of effect where JavaScript is the right tool, not CSS — don't force a discrete-<code>steps()</code> counter to fake smooth numeric counting when a small shared observer does it properly.</p>

<h2>10. Direction-Aware Grid Reveal (IntersectionObserver)</h2>

<p>Left-column cards slide in from the left, right-column cards from the right, and the middle column rises from below — one shared observer, each card's own direction read from a data attribute.</p>

<p><strong>How it works:</strong> the second deliberate JS counterpoint, and for a related but distinct reason from the counter above — this needs per-element branching logic, not just a value the timeline API can't compute. Each card carries a plain <code>data-from="left"</code>/<code>"right"</code>/<code>"up"</code> attribute, and one shared <code>IntersectionObserver</code> callback reads that attribute off whichever card just entered the viewport to decide which pre-set CSS transform to clear. A <code>view-timeline</code> could animate any one card's own entrance, but choosing a <em>different</em> starting transform per card based on a data attribute is exactly the kind of per-element conditional logic that stays firmly in JavaScript's territory rather than CSS's.</p>

<p><strong>Best for:</strong> a services or process-step grid where a uniform fade-up would look flatter than staggered per-column motion. <strong>Tip:</strong> keep the direction distances small (this uses 28–40px) — a direction-aware reveal reads as intentional at a subtle scale and as gimmicky at a large one.</p>

<h2>Final thought</h2>

<p>The real shift with the Scroll-Driven Animations API isn't that it makes existing effects prettier — it's that it moves an entire category of "listen to scroll, compute a progress value, apply it to a style" code out of JavaScript and onto the compositor, for free, with smoother behavior during fast or inertial scrolling than a hand-rolled listener usually achieves. But the two IntersectionObserver snippets in this batch aren't filler — they're the honest boundary of what the CSS-only approach can do today. A progress value the browser computes for you is not the same primitive as smooth numeric interpolation or per-element conditional logic, and knowing which side of that line a given effect falls on is the actual skill here, not just knowing the new syntax exists.</p>

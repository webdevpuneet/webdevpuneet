<h2>What actually makes a mobile mockup feel real</h2>

<p>Three ideas run through every screen below, and they're worth naming because they're what separates a screen that looks like an app from one that behaves like a picture of an app:</p>

<ul>
<li><strong>One function owns each piece of derived state.</strong> The checkout's <code>recalc()</code>, the onboarding's <code>go(i)</code>, the fitness rings' per-ring circumference math — each screen routes every interaction that changes a number or a position through a single function, so the UI can never show two numbers that disagree with each other.</li>
<li><strong>Motion confirms the action, not just decorates it.</strong> A heart that bursts on double-tap, a vinyl disc that only spins while playing, a progress bar that visibly fills before it auto-advances — each animation is reporting a state change, which is what makes tapping something feel like it worked.</li>
<li><strong>Real form controls under the hood.</strong> Radio buttons for payment methods, a real <code>&lt;form&gt;</code> for chat and login, disabled states on buttons that shouldn't be tappable yet — the phone-frame chrome is cosmetic, but the interactive elements underneath are genuine, focusable, accessible DOM.</li>
</ul>

<p>Keep those three in mind as you scroll — they're also exactly what to check for if you're evaluating whether a mockup is ready to hand to a developer.</p>

<p><strong>How it works:</strong> every slide sits in a flex track at <code>min-width: 100%</code>, and moving between them is a single <code>transform: translateX(-index * 100%)</code> on the track — there's no per-slide show/hide, just one number changing and CSS animating the rest. A single <code>go(i)</code> function is the only thing allowed to touch that index: the Next button, the Skip button, and a pointer-swipe gesture (comparing the start and end <code>clientX</code> against a 45px threshold) all call it, so the slide position, the progress dots, and the button label can never drift out of sync with each other. <p><strong>Best for:</strong> the very first screen of any app pitch or prototype. <strong>Tip:</strong> keep the slide count at three or four — a single <code>go()</code> function scales to any number, but attention for an intro carousel drops off fast past four screens.</p>

<h2>4. Mobile Feed Screen</h2>

<p>A social timeline: a horizontally scrolling story row, image posts with double-tap-to-like and a bursting heart, live like counts, and a bottom tab bar.</p>

<iframe src="https://fwdtools.com/ui-snippets/mobile-feed-screen/embed/" style="width:100%;height:640px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Mobile Feed Screen — Free HTML/CSS/JS Snippet by FWD Tools"></iframe>

<p><strong>How it works:</strong> the signature gesture is timing-based — a click on the media area records a timestamp, and if a second click lands within 320ms it counts as a double-tap, liking the post if it isn't already liked and replaying a heart-burst animation over the image. Replaying that animation on every double-tap (not just the first) needs a specific trick: the code removes the burst's CSS class, forces a synchronous reflow by reading <code>offsetWidth</code>, then re-adds the class — the standard way to restart a CSS animation that's already run once. The like count is parsed by stripping commas, incremented, and re-formatted with <code>toLocaleString()</code>, so "1,284 likes" correctly becomes "1,285" instead of "1284". Story rings fade from a vivid gradient to grey the moment they're tapped, exactly how real apps mark a story seen.</p>

<p><strong>Best for:</strong> any social or photo-sharing app's home screen. <strong>Tip:</strong> the double-tap gesture is layered on top of the like button, not instead of it — keep both so keyboard and assistive-tech users have a direct way to like a post.</p>

<h2>5. Mobile Stories Viewer</h2>

<p>A full-screen, self-driving slideshow: segmented progress bars that fill one at a time, tap zones to jump forward or back, hold-to-pause, and a reply bar.</p>

<iframe src="https://fwdtools.com/ui-snippets/mobile-stories-viewer/embed/" style="width:100%;height:640px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Mobile Stories Viewer — Free HTML/CSS/JS Snippet by FWD Tools"></iframe>

<p><strong>How it works:</strong> each segment's fill is a four-second CSS keyframe animation — there's no <code>setInterval</code> counting milliseconds anywhere. The browser owns the timing entirely; JavaScript only listens for the fill's <code>animationend</code> event and advances to the next slide when it fires, which keeps the story precisely in step with what's visually on screen. Two invisible buttons cover roughly the left and right third of the stage for previous and next, and navigating to any slide restarts its bar from zero using the same clear-reflow-reapply trick as the feed screen's heart burst. Hold-to-pause is pure CSS state: a <code>pointerdown</code> anywhere on the stage sets the active bar's <code>animation-play-state</code> to paused, which freezes the fill exactly where it is and resumes from that same point on release — no elapsed-time bookkeeping required.</p>

<p><strong>Best for:</strong> the natural next screen after a feed, or as a lighter, punchier alternative to a full onboarding carousel for a single feature highlight. <strong>Tip:</strong> the CSS-timed approach means pacing is trivial to change per slide — just vary that one keyframe's duration.</p>

<h2>7. Mobile Music Player Screen</h2>

<p>A full-screen now-playing view: a spinning vinyl disc that only turns while playing, a draggable seek bar, a real elapsed-time clock, and mode toggles.</p>

<iframe src="https://fwdtools.com/ui-snippets/mobile-music-player-screen/embed/" style="width:100%;height:640px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Mobile Music Player Screen — Free HTML/CSS/JS Snippet by FWD Tools"></iframe>

<p><strong>How it works:</strong> a single <code>render()</code> function is the only place that reads the elapsed seconds and writes the progress fill's width, the knob's position, and the formatted <code>m:ss</code> label — so those three outputs can never disagree. Play starts a one-second interval that advances the clock and calls <code>render()</code>; a class toggle on the album art flips the vinyl disc's rotation animation between <code>paused</code> and <code>running</code>, so it freezes and resumes from exactly where it stopped with zero extra JavaScript. The seek bar supports both a click-to-jump and a real knob drag using Pointer Events — the drag listens on <code>window</code>, not just the track, so the gesture keeps working even if the pointer slides off the bar mid-drag, and the resulting ratio is clamped to stay within 0 and 1.</p>

<p><strong>Best for:</strong> the now-playing screen behind a mini-player bar, or as a scrub-bar reference for any timed media UI. <strong>Tip:</strong> swap the <code>setInterval</code> clock for a real <code>&lt;audio&gt;</code> element's <code>timeupdate</code> event and the render function needs no changes — only the time source moves.</p>

<h2>8. Mobile Fitness Screen</h2>

<p>An activity-tracker home screen: three concentric SVG progress rings that sweep up from empty on load, a stat grid, and a workout history list.</p>

<iframe src="https://fwdtools.com/ui-snippets/mobile-fitness-screen/embed/" style="width:100%;height:640px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Mobile Fitness Screen — Free HTML/CSS/JS Snippet by FWD Tools"></iframe>

<p><strong>How it works:</strong> each ring is an SVG circle whose progress is drawn with the classic <code>stroke-dasharray</code>/<code>stroke-dashoffset</code> technique — the dash length is set to the circle's own circumference (<code>2πr</code>), and the offset shrinks toward zero to reveal more of the arc, rotated -90 degrees so it starts at twelve o'clock like a real wearable. Because the three rings have different radii, each needs its own circumference computed independently — sharing one value across all three would misalign the inner arcs at the same percentage. On load, the rings start fully offset, then a <em>double</em> <code>requestAnimationFrame</code> sets the real target offset on a later frame, which is what makes the browser register a genuine transition from empty to filled instead of just painting the final state instantly.</p>

<p><strong>Best for:</strong> fitness and health apps, or any goal-tracking UI that wants the "closing your rings" moment. <strong>Tip:</strong> the legend beside the rings already spells out each metric in text — treat that as the accessible source of truth and mark the decorative SVG <code>aria-hidden</code>.</p>

<h2>9. Mobile Banking Screen</h2>

<p>An account dashboard: a gradient balance card styled like a physical payment card, a hide-balance toggle that blurs every amount at once, a quick-action grid, and a color-coded transaction list.</p>

<iframe src="https://fwdtools.com/ui-snippets/mobile-banking-screen/embed/" style="width:100%;height:640px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Mobile Banking Screen — Free HTML/CSS/JS Snippet by FWD Tools"></iframe>

<p><strong>How it works:</strong> the privacy toggle is the detail worth studying — tapping the eye flips one shared <code>hidden</code> class across the balance and every transaction amount on the page, and that class doesn't replace the digits with dots, it sets their color to transparent and layers a soft <code>text-shadow</code> blur. The real numbers stay in the DOM the whole time, they just render as an unreadable smudge, which makes revealing them instant with no re-render — and income versus spending rows keep tinted blur shadows so the row's type is still hinted even while redacted. The balance card itself fakes a physical card with a large faded circle bleeding off one corner via an <code>::after</code> pseudo-element, layered behind the content with <code>z-index</code>. Quick-action taps get a tactile pulse from the Web Animations API (<code>element.animate()</code>) rather than a permanent state change, which is the right call for buttons that would navigate elsewhere in a real app.</p>

<p><strong>Best for:</strong> fintech and banking apps, or anywhere a screen needs a genuine privacy affordance. <strong>Tip:</strong> when you adapt this, also swap the accessible text while hidden — an <code>aria-label</code> like "balance hidden" — since the blur is purely visual and a screen reader would otherwise still announce the real figure.</p>

<h2>10. Mobile Checkout Screen</h2>

<p>The final step: an address card, cart items with quantity steppers, custom-styled payment radios, a working promo code, and a live-recalculating order summary under a sticky pay button.</p>

<iframe src="https://fwdtools.com/ui-snippets/mobile-checkout-screen/embed/" style="width:100%;height:640px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Mobile Checkout Screen — Free HTML/CSS/JS Snippet by FWD Tools"></iframe>

<p><strong>How it works:</strong> every cart item stores its unit price on a <code>data-price</code> attribute, and a single <code>recalc()</code> function is the only place any total gets computed — it walks the items, multiplies price by quantity, applies the current discount rate, adds flat shipping, and writes the subtotal, discount line, grand total, and the sticky bar's total all from that one pass. Every interaction that could change the total, whether a stepper tap or a promo code, calls this same function, which is what keeps the summary and the sticky bar from ever showing two different numbers. The minus stepper deliberately won't drop a quantity below one — that's a guard forcing an explicit remove action instead of an ambiguous zero. The promo code uppercases the input before comparing it, so "save10" and "SAVE10" both work, and gives three distinct states: applied, invalid, and empty, each with its own message.</p>

<p><strong>Best for:</strong> the final screen of any commerce flow, and a solid reference for centralizing totals instead of nudging a running number. <strong>Tip:</strong> the payment methods are genuine radio inputs styled with a <code>:checked ~</code> sibling selector, not divs with click handlers — keep that pattern, since it gives keyboard and screen-reader selection for free.</p>

<h2>A few mobile-UI principles worth keeping</h2>

<ul>
<li><strong>Route every derived value through one function.</strong> The checkout's totals, the fitness rings' offsets, the music player's progress bar — each is written by exactly one function, which is what makes them trustworthy under rapid interaction.</li>
<li><strong>Let CSS own timing wherever it can.</strong> The stories viewer's auto-advance and the music player's vinyl spin both hand timing to the browser's animation engine instead of a JavaScript timer, which is both simpler code and a smoother result.</li>
<li><strong>Redact without destroying data.</strong> The banking screen's blur-not-replace approach to hiding numbers is a broadly useful pattern anywhere sensitive data needs an instant, reversible hide.</li>
<li><strong>Confirm every tap.</strong> A bursting heart, a pulsing icon, a flashing row — the fastest way to make an interface feel responsive is to never leave a tap without a visible reaction.</li>
</ul>

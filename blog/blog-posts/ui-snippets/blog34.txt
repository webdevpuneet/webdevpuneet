<h2>1. JWT Decoder &amp; Inspector</h2>

<p>Paste any JSON Web Token and get its header, payload, and signature decoded live, with automatic expiry detection — entirely client-side, no token ever leaves the page.</p>

<iframe src="https://fwdtools.com/ui-snippets/jwt-decoder/embed/" style="width:100%;height:640px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="JWT Decoder & Inspector — Free HTML CSS JS Snippet by FWD Tools"></iframe>

<p><strong>How it works:</strong> a JWT's three segments are base64url-encoded, not plain base64 — RFC 4648 §5 swaps <code>+</code>/<code>/</code> for <code>-</code>/<code>_</code> and drops padding so the token is URL-safe. Since the browser's <code>atob()</code> only understands standard base64, <code>base64UrlDecode()</code> reverses those substitutions and re-pads to a multiple of four characters first, then decodes the resulting binary string through a <code>Uint8Array</code> and <code>TextDecoder('utf-8')</code> — skipping that byte-array round trip is exactly what makes naive decoders mangle unicode names in claim values. The header and payload are <code>JSON.parse</code>d in <em>separate</em> try/catch blocks, so a corrupted payload doesn't hide a perfectly valid header. Expiry is checked against the <code>exp</code> claim — a Unix timestamp in seconds per RFC 7519 — compared to <code>Math.floor(Date.now() / 1000)</code>, flipping the badge to an amber "Expired" state the moment it's past due.</p>

<p><strong>Best for:</strong> debugging an auth integration straight from a token copied out of a network tab, or teaching that a JWT is just three readable JSON blobs joined by dots, not an opaque encrypted blob. <strong>Tip:</strong> the signature panel is intentionally display-only — verifying it needs the signing secret or public key, which a client-side tool should never ask you to paste in.</p>

<h2>3. CIDR / Subnet Calculator</h2>

<p>Enter an address in CIDR notation and get the network address, broadcast address, subnet mask, wildcard mask, and usable host range — computed with real 32-bit bitwise arithmetic, not a lookup table.</p>

<iframe src="https://fwdtools.com/ui-snippets/cidr-subnet-calculator/embed/" style="width:100%;height:600px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="CIDR / Subnet Calculator — Free HTML CSS JS Snippet by FWD Tools"></iframe>

<p><strong>How it works:</strong> the IPv4 address is packed into a single 32-bit integer via <code>ipToInt()</code>, and the subnet mask is derived as <code>(0xFFFFFFFF &lt;&lt; (32 - prefix)) &gt;&gt;&gt; 0</code> — a left-shift by however many host bits the prefix leaves, with the unsigned-right-shift-by-zero trick to force the result back into an unsigned 32-bit range (JavaScript's bitwise operators otherwise treat the result as signed). The network address is <code>ipInt &amp; maskInt</code>, the broadcast address is <code>networkInt | (~maskInt &gt;&gt;&gt; 0)</code>, and usable host count is <code>2^(32-prefix) - 2</code> — the same arithmetic any router performs, made visible. The two boundary cases are handled explicitly rather than falling out of the general formula: a <code>/32</code> is a single host route with no broadcast distinction, and a <code>/31</code> is a point-to-point link (RFC 3021) where both addresses are usable with no reserved broadcast.</p>

<p><strong>Best for:</strong> planning a VPC or subnet layout, or checking whether two address ranges overlap before assigning them. <strong>Tip:</strong> the binary breakdown row shows exactly which bits belong to the network portion versus the host portion — useful for building intuition about why a given prefix produces the host count it does.</p>

<p>Grab the code: <a href="https://fwdtools.com/ui-snippets/cidr-subnet-calculator/">CIDR / Subnet Calculator</a></p>

<h2>4. UUID / ULID Generator &amp; Validator</h2>

<p>Generate cryptographically random UUID v4s or time-sortable ULIDs, bulk-generate up to 100 at once, and validate a pasted identifier against both formats.</p>

<iframe src="https://fwdtools.com/ui-snippets/uuid-ulid-generator/embed/" style="width:100%;height:600px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="UUID / ULID Generator & Validator — Free HTML CSS JS Snippet by FWD Tools"></iframe>

<p><strong>How it works:</strong> UUID v4 generation prefers <code>crypto.randomUUID()</code> where available, falling back to <code>crypto.getRandomValues()</code> on 16 raw bytes with the version and variant bits set by hand — <code>bytes[6] = (bytes[6] &amp; 0x0f) | 0x40</code> forces the version-4 nibble, and <code>bytes[8] = (bytes[8] &amp; 0x3f) | 0x80</code> forces the RFC 4122 variant bits, which is what makes the output a spec-correct UUID v4 rather than just 16 random bytes formatted with dashes. ULID generation packs the current millisecond timestamp into 6 bytes and 10 bytes of cryptographic randomness, then encodes the combined 128 bits through Crockford's Base32 alphabet (which excludes visually ambiguous characters like <code>I</code>, <code>L</code>, <code>O</code>, and <code>U</code>) five bits at a time — the timestamp prefix is exactly why ULIDs sort lexicographically in the same order they were created, unlike UUIDs.</p>

<p><strong>Best for:</strong> generating primary keys or idempotency keys during development, or quickly checking whether a string a teammate pasted into Slack is actually a valid identifier before debugging further. <strong>Tip:</strong> reach for ULID over UUID v4 specifically when you need IDs that sort chronologically in a database index — the embedded timestamp does that for free.</p>

<p><strong>How it works:</strong> plain <code>btoa()</code> throws on any character outside the Latin-1 range, which is why <code>utf8ToB64()</code> first runs the input through <code>new TextEncoder().encode()</code> to get real UTF-8 bytes before base64-encoding them — the same unicode-safety gap the JWT decoder above solves from the decode side. <p><strong>Best for:</strong> quickly checking what a base64 blob actually contains, or converting a string to the URL-safe variant needed for a query parameter or a JWT segment. <strong>Tip:</strong> the URL-safe toggle re-encodes or re-decodes automatically the moment you switch it, so you can compare both variants of the same input without retyping anything.</p>

<h2>7. Violin Plot Chart</h2>

<p>Four groups of response-time data rendered as real violin shapes — width at each height genuinely reflects how common that value was, computed with a from-scratch Gaussian kernel density estimate.</p>

<iframe src="https://fwdtools.com/ui-snippets/violin-plot-chart/embed/" style="width:100%;height:560px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Violin Plot Chart — Free HTML CSS JS Snippet by FWD Tools"></iframe>

<p><strong>How it works:</strong> <code>kde()</code> evaluates a genuine Gaussian kernel density estimate at 60 points spanning each group's value range, summing a bell-curve contribution from every raw sample at every evaluation point and normalizing by sample count and bandwidth — the textbook KDE formula, not an approximation. Bandwidth (how smoothed the resulting curve looks) is derived per group as roughly one-ninth of that group's own value spread, so a tightly-clustered group and a widely-spread group each get proportionally appropriate smoothing automatically instead of one fixed constant that over- or under-smooths depending on the data. The resulting density values become horizontal half-widths, scaled relative to that group's own peak density, then mirrored left and right of the group's center and joined into one closed SVG path — that mirroring is what produces the classic symmetric violin silhouette. A white bar marking the median is computed separately via linear-interpolation quantile estimation, not just the middle array index.</p>

<p><strong>Best for:</strong> comparing full distribution shape across categories — not just an average — where a bar chart would hide whether a group is bimodal, tightly clustered, or has a long tail. <strong>Tip:</strong> swap the synthetic <code>gen()</code> calls for your own raw sample arrays — any plain array of numbers works directly with both <code>kde()</code> and <code>quantile()</code> with no other changes needed.</p>

<p><strong>How it works:</strong> each axis independently normalizes its own values to a 0-to-1 fraction via <code>normalize()</code>, using that axis's own configured min and max — so dollars, hours, and kilograms never need to share a unit, only a 0-to-1 fraction, before <code>valueY()</code> maps that fraction onto the same shared pixel height every axis uses. <h2>9. Chord Diagram Chart</h2>

<p>A circular diagram showing how items moved between four teams — ribbon thickness genuinely reflects the transferred amount, computed directly from a raw adjacency matrix, with hover-to-isolate on any group's flows.</p>

<iframe src="https://fwdtools.com/ui-snippets/chord-diagram-chart/embed/" style="width:100%;height:560px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Chord Diagram Chart — Free HTML CSS JS Snippet by FWD Tools"></iframe>

<p><strong>How it works:</strong> the entire diagram is driven by one plain 2D array, <code>matrix[i][j]</code>, read as "items handed off from group i to group j." Each group's outer arc length is proportional to its row-plus-column total (everything it sent and received), and that arc subdivides into sub-segments proportional to each individual flow — outgoing amounts first, then incoming — so the arc itself already visually communicates a group's send/receive balance before a single ribbon is drawn. Ribbons connecting two groups are built as one curved path per unordered pair, with both the i→j and j→i values folded into a single ribbon width, then rendered as a quadratic Bézier curve — a single control point placed exactly at the diagram's center — so the connections read as flowing through the middle rather than as straight chords cutting across it.</p>

<p><strong>Best for:</strong> visualizing flow or exchange between a small number of categories — support tickets moving between teams, funds moving between accounts, traffic moving between page sections — where a matrix table alone doesn't communicate scale as immediately. <strong>Tip:</strong> chord diagrams stop being readable past roughly six to eight groups; for larger relational datasets, a <a href="https://fwdtools.com/ui-snippets/sankey-diagram/">Sankey-style flow</a> diagram or a plain heatmap of the same matrix communicates better.</p>

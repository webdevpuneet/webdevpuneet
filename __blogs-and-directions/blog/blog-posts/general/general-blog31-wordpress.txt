<!-- wp:paragraph -->
<p>A form is the single most abandoned piece of UI on the web, and the reason is rarely the fields themselves &mdash; it's the feedback around them. A generic "invalid input" banner at the top leaves the user hunting for what actually went wrong. A field that clears itself after an error erases five minutes of typing over one missing character. A submit button with no reaction to a click gets clicked three more times. None of this requires a redesign to fix &mdash; it's a known set of interaction patterns, each solving one specific moment of doubt a user hits while filling something out. This post is a gallery of twelve distinct form UX patterns, each implemented in plain HTML, CSS and vanilla JavaScript, so you can see exactly how each one is built and which specific problem it solves.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>Every demo below is <strong>live and interactive</strong> right here in the article &mdash; type into the actual input, click the actual button, and watch the pattern react in real time, the same way it would in a production form. Every embed also has a <strong>Fork &amp; Edit</strong> button that opens the exact code, already running, in <a href="https://webdevpuneet.com/ui-snippets/mycode/">My Code</a> &mdash; webdevpuneet's free in-browser editor. Change a regex, swap a threshold, delete a transition &mdash; that's a faster way to understand why a pattern feels right than any explanation.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->

The <a href="https://webdevpuneet.com/js-playground/">JavaScript Playground</a> is a free, click-based, in-browser course that covers the event handling, DOM updates and state tracking every pattern below is built from, one guided step at a time.</p>

<!-- wp:heading -->
<h2 class="wp-block-heading">Why form feedback matters more than form design</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Most of the friction in a form isn't the number of fields &mdash; it's how much doubt the user has to sit with between typing something and finding out whether it worked. Every pattern below closes that gap in a different place: some validate the instant you type, so an error is caught before you've moved to the next field; some preview what you'll get before you commit, like a strength meter or a live-formatted card number; some just make the interface honest about what's happening, like a disabled button that visibly says it's working instead of going silently unresponsive. None of these are exotic &mdash; they're small, well-understood conventions users already recognize from other products, which is exactly why they lower cognitive load instead of adding to it. Knowing which moment of doubt a given field creates is what determines which pattern below actually fixes it.</p>
<!-- /wp:paragraph -->

<!-- wp:heading -->
<h2 class="wp-block-heading">1. Real-Time Inline Validation</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Type into the email field &mdash; you'll see it validate as you type, not just after you hit submit. Try "a", then "a@b", then a full address.</p>
<!-- /wp:paragraph -->

<!-- wp:html -->
<iframe src="https://webdevpuneet.com/demos/a1/30/1.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Real-Time Inline Validation Demo by webdevpuneet.com"></iframe>
<!-- /wp:html -->

<!-- wp:paragraph -->
<p><strong>How it works:</strong></p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>function checkEmail(val) {
  var trimmed = val.trim();
  if (!trimmed) return { state: '', text: ' ' };
  var ok = /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(trimmed);
  if (ok) return { state: 'valid', text: '✓ Looks good' };
  if (trimmed.indexOf('@') === -1) return { state: 'invalid', text: 'Missing the @ symbol' };
  return { state: 'invalid', text: 'Enter a complete email address' };
}</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>The field's <code>input</code> event fires on every keystroke, and each time it runs the same check the submit handler would eventually run &mdash; the only difference is when the result gets shown. That timing shift is the whole pattern: instead of a user discovering an error after committing to the entire form and clicking submit, they see it the moment it becomes true, while the field is still in front of them and the fix is a single keystroke away. The check itself is deliberately specific rather than a single pass/fail &mdash; noticing there's no "@" yet produces a more useful message than a blanket "invalid," because it tells the user exactly what's still missing instead of making them guess. Trimming whitespace before testing also matters here; rejecting a technically valid address over a leading or trailing space that autofill or a paste commonly introduces is a false negative, not real validation.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p><strong>Best for:</strong> any field with a checkable format &mdash; email, username availability, phone number &mdash; where an error is cheap to catch immediately and expensive to catch later. <strong>Tip:</strong> validate on <code>input</code> only after the field has content; validating an empty field the instant it's focused just shows an error before the user has done anything wrong.</p>
<!-- /wp:paragraph -->

<h2 class="wp-block-heading">2. Password Strength Meter</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Type a password &mdash; the bar and label update live as you type, before you ever submit anything. Try something short, then add numbers, symbols and mixed case.</p>
<!-- /wp:paragraph -->

<!-- wp:html -->
<iframe src="https://webdevpuneet.com/demos/a1/30/2.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Password Strength Meter Demo by webdevpuneet.com"></iframe>
<!-- /wp:html -->

<!-- wp:paragraph -->
<p><strong>How it works:</strong></p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>function score(val) {
  if (!val) return 0;
  var points = 0;
  if (val.length &gt;= 8) points++;
  if (val.length &gt;= 12) points++;
  if (/[a-z]/.test(val) && /[A-Z]/.test(val)) points++;
  if (/[0-9]/.test(val)) points++;
  if (/[^A-Za-z0-9]/.test(val)) points++;
  return Math.min(points, 5);
}</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>Each criterion the password meets &mdash; length past 8, length past 12, mixed case, a digit, a symbol &mdash; adds one point, and the total maps to a five-level bar with its own color and label. The value of showing this live, rather than only after a failed submit, is that it turns "make a stronger password" from an abstract instruction into an immediate, visible consequence of what's already been typed: add a number and the bar visibly moves. That feedback loop is what gets users to actually improve a weak password in place, instead of submitting a weak one and being told after the fact to try again. The scoring here is a simplified stand-in for what real strength meters typically use &mdash; a library like zxcvbn that also checks against common password lists and predictable patterns &mdash; but the interaction principle is identical regardless of how sophisticated the scoring function is.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p><strong>Best for:</strong> any account-creation or password-change form where users are choosing their own password rather than receiving one. <strong>Tip:</strong> a strength meter should guide, not gate &mdash; pair it with a real minimum requirement enforced on submit, but never block a technically strong password just because the meter's heuristic scored it a level lower than expected.</p>
<!-- /wp:paragraph -->

<h2 class="wp-block-heading">3. Show/Hide Password Toggle</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Type something into the field, then click the eye icon to reveal it as plain text, and click again to mask it.</p>
<!-- /wp:paragraph -->

<!-- wp:html -->
<iframe src="https://webdevpuneet.com/demos/a1/30/3.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Show/Hide Password Toggle Demo by webdevpuneet.com"></iframe>
<!-- /wp:html -->

<!-- wp:paragraph -->
<p><strong>How it works:</strong></p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>eyeBtn.addEventListener('click', function () {
  visible = !visible;
  pw.type = visible ? 'text' : 'password';
  eyeIcon.innerHTML = visible ? SLASH : OPEN;
  eyeBtn.setAttribute('aria-pressed', visible ? 'true' : 'false');
});</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>The entire mechanism is one line &mdash; flipping the input's <code>type</code> attribute between <code>password</code> and <code>text</code> &mdash; but that single toggle solves a genuinely common failure mode: a masked password field with no visibility check means a typo goes unnoticed until the login or signup attempt fails, at which point the user has no idea whether they mistyped the password or something else broke. Letting users briefly see what they typed removes that ambiguity entirely, at the cost of the field being readable if someone happens to be looking at the screen &mdash; a trade-off worth making by default, since it's user-initiated and reversible with one more click. Setting <code>aria-pressed</code> on the button is what makes the toggle's current state legible to assistive technology, not just to sighted users watching the icon swap.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p><strong>Best for:</strong> any password field, especially on mobile where fat-finger typos on a small keyboard are common and masked text makes them invisible. <strong>Tip:</strong> default the field to masked, never revealed &mdash; the toggle should always be an opt-in the user reaches for, not a surprise default that exposes a password on a shared or public screen.</p>
<!-- /wp:paragraph -->

<h2 class="wp-block-heading">4. Floating Label Inputs</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Click into the field &mdash; the placeholder animates up into a label above the input instead of just disappearing.</p>
<!-- /wp:paragraph -->

<!-- wp:html -->
<iframe src="https://webdevpuneet.com/demos/a1/30/4.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Floating Label Inputs Demo by webdevpuneet.com"></iframe>
<!-- /wp:html -->

<!-- wp:paragraph -->
<p><strong>How it works:</strong></p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>.field:focus + .floatLabel,
.field:not(:placeholder-shown) + .floatLabel {
  top: 7px;
  transform: scale(0.72);
  color: var(--accent);
}</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>A plain placeholder has a well-known problem: once the user starts typing, the label disappears with it, so if they get interrupted or scroll back up, the field's purpose is gone along with the text that was standing in for it. A floating label fixes this by being a real, permanently visible <code>&lt;label&gt;</code> element that simply repositions &mdash; sitting inside the field as a placeholder-style hint when empty and unfocused, then animating up above the input the moment it's focused or has content, using nothing but the adjacent-sibling selector and the <code>:placeholder-shown</code> pseudo-class (which requires the input's actual placeholder to be a single space, a small but necessary trick). No JavaScript is needed to drive the animation at all &mdash; it's a pure CSS state machine keyed off two selectors the browser already tracks. The result keeps the field's label permanently legible without spending the vertical space a static label above every field would cost.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p><strong>Best for:</strong> compact forms, login screens, and any layout where space is tight enough that a permanently visible label above every field feels heavy. <strong>Tip:</strong> keep the floated label's contrast and size legible at its shrunken scale &mdash; a label that becomes too small or too light once it floats defeats the purpose of keeping it visible in the first place.</p>
<!-- /wp:paragraph -->

<!-- wp:heading -->
<h2 class="wp-block-heading">5. Card Number Input Masking</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Type digits into the field &mdash; they're auto-grouped into 4-digit blocks as you type, the way a real card number reads.</p>
<!-- /wp:paragraph -->

<!-- wp:html -->
<iframe src="https://webdevpuneet.com/demos/a1/30/5.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Card Number Input Masking Demo by webdevpuneet.com"></iframe>
<!-- /wp:html -->

<!-- wp:paragraph -->
<p><strong>How it works:</strong></p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>function formatCard(raw) {
  var digits = raw.replace(/\D/g, '').slice(0, 16);
  var groups = [];
  for (var i = 0; i &lt; digits.length; i += 4) groups.push(digits.slice(i, i + 4));
  return groups.join(' ');
}</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>Every keystroke strips the field down to its raw digits, caps it at 16, then rebuilds it as space-separated groups of four before writing it back into the input &mdash; so what the user sees always matches the familiar printed layout of a physical card, regardless of whether they typed the spaces themselves. This is input masking's core value: it removes an entire category of formatting mistake by never asking the user to type the formatting at all, while also making a 16-digit string dramatically easier to visually verify before submitting, since four-digit chunks are far easier for a human eye to scan and catch a transposed digit in than one unbroken run of sixteen. The same technique &mdash; strip to raw characters, re-render in a fixed pattern &mdash; applies directly to phone numbers, dates and any other input with a conventional printed shape.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p><strong>Best for:</strong> card numbers, phone numbers, and any input with a widely recognized printed format the user already expects to see reflected back. <strong>Tip:</strong> always store and submit the raw, unformatted digits &mdash; the mask is a display convenience, and validation or submission logic should never depend on the spaces being present.</p>
<!-- /wp:paragraph -->

<h2 class="wp-block-heading">6. Character Counter with Color Warning</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Type into the bio field &mdash; the counter turns amber as you approach the limit and red once you're over it, well before you try to submit.</p>
<!-- /wp:paragraph -->

<!-- wp:html -->
<iframe src="https://webdevpuneet.com/demos/a1/30/6.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Character Counter with Color Warning Demo by webdevpuneet.com"></iframe>
<!-- /wp:html -->

<!-- wp:paragraph -->
<p><strong>How it works:</strong></p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>function update() {
  var len = bio.value.length;
  counter.textContent = len + ' / ' + LIMIT;
  var cls = 'counter';
  if (len &gt; LIMIT) cls += ' over';
  else if (len &gt;= LIMIT * 0.85) cls += ' warn';
  counter.className = cls;
}</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>A raw "140 / 500" counter technically conveys the same information at every character count, but it puts equal visual weight on "plenty of room left" and "about to run out" &mdash; the reader has to do the subtraction themselves to know how urgent it is. Color removes that arithmetic: neutral gray while there's comfortable room, amber once the count crosses roughly 85% of the target, red the moment it's exceeded. That gradient gives a glanceable sense of urgency without the user having to read the numbers at all, which matters most in a form with several fields where a counter easily goes unread in plain text. Keeping the counter tied to a soft target below the field's hard <code>maxlength</code> also matters &mdash; it lets users keep typing past the suggested length if they need to, while still steering most of them toward a concise answer.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p><strong>Best for:</strong> bios, tweet-style posts, SMS-length messages, and any field with a soft or hard length target the user should stay aware of while composing. <strong>Tip:</strong> never rely on color alone &mdash; pair it with the visible number, since color-only feedback is invisible to colorblind users and to anyone glancing at a low-contrast screen.</p>
<!-- /wp:paragraph -->

<h2 class="wp-block-heading">7. Segmented OTP Input</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Type a digit into the first box &mdash; focus auto-advances to the next box. Backspace on an empty box jumps back one, and pasting a full code fills every box at once.</p>
<!-- /wp:paragraph -->

<!-- wp:html -->
<iframe src="https://webdevpuneet.com/demos/a1/30/7.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Segmented OTP Input Demo by webdevpuneet.com"></iframe>
<!-- /wp:html -->

<!-- wp:paragraph -->
<p><strong>How it works:</strong></p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>box.addEventListener('input', function () {
  box.value = box.value.replace(/\D/g, '').slice(0, 1);
  if (box.value && boxes[i + 1]) boxes[i + 1].focus();
});
box.addEventListener('keydown', function (e) {
  if (e.key === 'Backspace' && !box.value && boxes[i - 1]) boxes[i - 1].focus();
});</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>Six single-character inputs stand in for one six-digit code, and each box's own <code>input</code> event is what drives the interaction &mdash; the instant a digit lands, focus jumps to the next box automatically, so the user never has to manually tab between them. Backspace on an already-empty box moving focus back one is what makes correcting a mistake feel natural rather than requiring a mouse click to re-select the right box. The paste handler exists because this pattern's most common real use &mdash; a code delivered by SMS or email &mdash; is almost always copied rather than typed, and a segmented input that can't accept a full pasted string forces users into typing each digit by hand, defeating the format's entire convenience. The visual segmentation itself also reduces transcription error: a code broken into six distinct boxes is easier to read back correctly from a notification than the same six digits run together.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p><strong>Best for:</strong> one-time passcodes, two-factor codes, and any fixed-length numeric code delivered externally that the user needs to re-enter. <strong>Tip:</strong> always wire up the paste handler &mdash; a user who received the code by SMS is going to try pasting it before they try typing it, and a segmented input that silently fails to accept a paste reads as broken. Add <code>autocomplete="one-time-code"</code> to the first box as well, so iOS and Android can offer the incoming SMS code as a one-tap suggestion.</p>
<!-- /wp:paragraph -->

<h2 class="wp-block-heading">8. Auto-Growing Textarea</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Type a few lines, then keep going past the visible edge &mdash; the box grows taller to fit instead of showing an internal scrollbar.</p>
<!-- /wp:paragraph -->

<!-- wp:html -->
<iframe src="https://webdevpuneet.com/demos/a1/30/8.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Auto-Growing Textarea Demo by webdevpuneet.com"></iframe>
<!-- /wp:html -->

<!-- wp:paragraph -->
<p><strong>How it works:</strong></p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>function resize() {
  note.style.height = 'auto';
  note.style.height = Math.min(note.scrollHeight, 220) + 'px';
}
note.addEventListener('input', resize);</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>Resetting the height to <code>auto</code> before reading <code>scrollHeight</code> is the part that's easy to miss and essential to the effect &mdash; without that reset, the browser reports the textarea's current fixed height back to itself, and the box can grow but never shrink again after a long paragraph is deleted. With the reset in place, every keystroke briefly collapses the box to its natural content height, reads how tall the content actually needs, then sets the height to match, capped at a maximum so a genuinely huge paste still gets an internal scrollbar rather than swallowing the whole page. The advantage over a fixed-height textarea with its own scrollbar is that the user can always see everything they've written at once while composing, rather than losing the beginning of a long message to an internal scroll region the moment it grows past a few lines.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p><strong>Best for:</strong> comments, messages, and any free-text field where the amount a user will write is genuinely unpredictable. <strong>Tip:</strong> always keep a <code>max-height</code> with <code>overflow</code> re-enabled past it &mdash; an unbounded auto-growing textarea on a very long paste can grow taller than the viewport and push the rest of the form off screen.</p>
<!-- /wp:paragraph -->

<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Click "Next" to move through the steps &mdash; the indicator marks exactly which step you're on and which are already complete.</p>
<!-- /wp:paragraph -->

<!-- wp:html -->
<iframe src="https://webdevpuneet.com/demos/a1/30/9.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Multi-Step Progress Indicator Demo by webdevpuneet.com"></iframe>

<!-- wp:paragraph -->

<!-- /wp:paragraph -->

<p>Each step dot carries one of three states &mdash; done, active, or upcoming &mdash; derived purely from comparing its own index against the current step number, and re-rendering all of them on every navigation is cheap enough that there's no need for more complex state tracking. What this buys the user is something a single "Step 2" text label doesn't: a spatial sense of how much is left, at a glance, without reading anything. A four-step form and a nine-step form communicate very different commitments even before the user reads a single field, and a progress indicator is what lets them make that judgment up front instead of discovering the form's true length one step at a time. Completed steps rendering as a checkmark rather than just a different color also reassures the user that earlier answers were actually captured, not just visually passed through.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p><strong>Best for:</strong> checkout flows, onboarding wizards, and any form long enough that splitting it into steps reduces the up-front intimidation of one long scroll. <strong>Tip:</strong> keep total step count visible from the very first step &mdash; showing "Step 1" with no indication of how many steps exist in total is worse than a single long form, since it removes the ability to judge the commitment at all.</p>
<!-- /wp:paragraph -->

<!-- wp:html -->
<iframe src="https://webdevpuneet.com/demos/a1/30/10.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Field-Specific Error Messages Demo by webdevpuneet.com"></iframe>
<!-- /wp:html -->

<p><strong>How it works:</strong></p>
<!-- /wp:paragraph -->

This is a small implementation difference from a top-of-form banner &mdash; a per-field error element instead of one shared one &mdash; but it's the difference between a form that tells the user what's wrong and one that just tells them something is wrong.</p>

<!-- wp:paragraph -->

<h2 class="wp-block-heading">11. Preserving Input Across Validation Errors</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Fill in the name and message, leave the email blank, then submit &mdash; only the email field flags an error; your other answers stay exactly as typed.</p>
<!-- /wp:paragraph -->

<!-- wp:html -->
<iframe src="https://webdevpuneet.com/demos/a1/30/11.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Preserving Input Across Validation Errors Demo by webdevpuneet.com"></iframe>
<!-- /wp:html -->

<!-- wp:paragraph -->
<p><strong>How it works:</strong></p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>form.addEventListener('submit', function (e) {
  e.preventDefault();
  // Only femail is ever touched here -- fname.value and fmsg.value
  // are never read, cleared, or reset by this handler at all.
  if (!ok) { femail.className = 'field error'; femail.focus(); return; }
});</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>The important thing about this demo's code is what it doesn't do: the submit handler only ever reads and writes the one field that actually failed, and never touches the others in any way, which means there's nothing in the logic capable of clearing them even by accident. This matters because the far more common failure mode isn't a deliberate "clear the form on error" decision &mdash; it's a handler that re-renders the entire form from a fresh state object on every submission attempt, silently dropping whatever the user had typed into fields that were never invalid in the first place. A user who's filled out eight fields correctly and gotten one wrong has already invested real effort; making them retype the other seven because of one mistake is one of the fastest ways to turn a fixable error into an abandoned form entirely.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p><strong>Best for:</strong> any form with more than a couple of fields, especially longer ones like signup, checkout or contact forms where retyping everything is a genuine cost. <strong>Tip:</strong> build validation as a per-field check that touches only the field it's checking &mdash; never as a full-form reset-and-rebuild, which is what accidentally wipes valid answers in the first place.</p>
<!-- /wp:paragraph -->

<!-- wp:heading -->
<h2 class="wp-block-heading">12. Submit Button Loading State</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Fill in the field (or leave it) and click "Submit" &mdash; the button disables and shows a spinner while the form fakes a network round trip, then confirms.</p>
<!-- /wp:paragraph -->

<!-- wp:html -->
<iframe src="https://webdevpuneet.com/demos/a1/30/12.html" style="width:100%;height:480px;border:0;border-radius:10px;overflow:hidden;" loading="lazy" title="Submit Button Loading State Demo by webdevpuneet.com"></iframe>
<!-- /wp:html -->

<!-- wp:paragraph -->
<p><strong>How it works:</strong></p>
<!-- /wp:paragraph -->

<!-- wp:code -->
<pre class="wp-block-code"><code>submitBtn.disabled = true;
btnLabel.innerHTML = '&lt;span class="spinnerSm"&gt;&lt;/span&gt; Submitting…';

setTimeout(function () {
  submitBtn.className = 'submitBtn done';
  btnLabel.textContent = '✓ Submitted';
}, 1500);</code></pre>
<!-- /wp:code -->

<!-- wp:paragraph -->
<p>This is the same disabled-plus-spinner mechanism that applies to any save action, narrowed to the specific moment a form is handed off &mdash; the button that was just clicked becomes the loading indicator, immediately disabled so a second click can't fire a duplicate submission while the first request is still in flight. For a form specifically, that duplicate-submit risk is higher stakes than most buttons: a double-submitted payment, signup or order isn't just a wasted request, it's often a real problem for the backend to deduplicate after the fact. Fixing the button's width before the label text changes length (from "Submit" to "Submitting…" to "Submitted") is what keeps the button from visibly resizing at each stage, which would otherwise make an already brief interaction feel jumpy.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p><strong>Best for:</strong> every form submission without exception &mdash; payment, signup, checkout, contact, and anything else a user might otherwise click twice. <strong>Tip:</strong> always disable the actual button element, not just overlay a spinner on top of it &mdash; a spinner sitting over a still-clickable button is one of the most common sources of duplicate form submissions in production.</p>
<!-- /wp:paragraph -->

<!-- wp:heading -->
<h2 class="wp-block-heading">Common pitfalls</h2>
<!-- /wp:heading -->

<!-- wp:list -->
<ul class="wp-block-list">
<!-- wp:list-item -->
<li><strong>Validating too aggressively while the user is still typing the first character.</strong> Flashing an error the instant a field gains focus, before the user has typed anything wrong, trains people to ignore validation messages entirely &mdash; wait for real content, or for blur, before judging a field.</li>
<!-- /wp:list-item -->
<!-- wp:list-item -->
<li><strong>Clearing the whole form when only one field fails.</strong> Re-rendering the entire form from scratch on a failed submission is what silently wipes valid answers along with the invalid one &mdash; demo #11 shows why touching only the failing field avoids this entirely.</li>
<!-- /wp:list-item -->
<!-- wp:list-item -->
<li><strong>A single generic "invalid input" message with no field reference.</strong> A banner at the top of a multi-field form forces the user to hunt for what's actually wrong &mdash; demo #10's per-field messages remove that search entirely.</li>
<!-- /wp:list-item -->
<!-- wp:list-item -->
<li><strong>No visible required-field indicator before submission.</strong> If "required" is only discovered as an error after a failed submit, the user is debugging your form instead of filling it out &mdash; mark required fields clearly up front, before anyone has a chance to skip one.</li>
<!-- /wp:list-item -->
<!-- wp:list-item -->
<li><strong>Disabling submit with no explanation of why.</strong> A grayed-out button and no label change reads as broken, not busy &mdash; demo #12's spinner-plus-text-change combination is what keeps a disabled control legible instead of looking frozen.</li>
<!-- /wp:list-item -->
</ul>
<!-- /wp:list -->

<!-- wp:heading -->
<h2 class="wp-block-heading">Frequently asked questions</h2>
<!-- /wp:heading -->

<!-- wp:heading {"level":3} -->
<h3 class="wp-block-heading">Should I validate on input, on blur, or only on submit?</h3>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Validate on <code>blur</code> for the first pass on any given field &mdash; it catches an error the moment the user moves on without interrupting them mid-keystroke. Once a field has already shown an error, switch to validating on <code>input</code> for that field specifically, so the message disappears the instant it's actually fixed rather than lingering until the next blur. Reserve submit-time validation as the final safety net that catches anything skipped, not as the primary mechanism &mdash; by the time submit fires, most errors should already be visible. For styling alone, CSS can now do this "only after the user has interacted" timing for you: <code>:user-invalid</code> (supported in every major browser since 2023) matches a field only once the user has changed it or tried to submit, unlike <code>:invalid</code>, which is true from page load.</p>
<!-- /wp:paragraph -->

<!-- wp:heading {"level":3} -->
<h3 class="wp-block-heading">How do I make validation errors accessible to screen reader users?</h3>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Associate each error message with its field using <code>aria-describedby</code>, and mark the field itself with <code>aria-invalid="true"</code> while the error is active, so a screen reader announces both the field's state and the reason together. Wrapping the error text in a live region (<code>aria-live="polite"</code>) also ensures newly appearing messages get announced even when focus hasn't moved, which matters for errors surfaced by a submit attempt rather than a blur on the specific field.</p>
<!-- /wp:paragraph -->

<!-- wp:heading {"level":3} -->
<h3 class="wp-block-heading">Are password strength meters mandatory, or just a suggestion?</h3>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>They're a suggestion, and should stay one &mdash; a strength meter's job is to guide the user toward a stronger password in the moment, not to gate submission on its own heuristic. The actual requirement enforced on submit should be a separate, explicit rule (minimum length, for instance), because a scoring algorithm's opinion of "strong enough" is inherently approximate and shouldn't be the sole gatekeeper for something as consequential as account access.</p>
<!-- /wp:paragraph -->

<!-- wp:heading {"level":3} -->
<h3 class="wp-block-heading">Why does input masking format as you type instead of after you submit?</h3>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Formatting at submit time means the user spends the entire time they're typing looking at an unformatted string, which is exactly when a formatted view is most useful for catching a typo. Formatting live, as demo #5 does for a card number, means what's on screen while typing already matches the shape the user recognizes, so a mistake is visible immediately rather than only after the fact.</p>
<!-- /wp:paragraph -->

<!-- wp:heading {"level":3} -->
<h3 class="wp-block-heading">Do all twelve of these patterns belong in every form?</h3>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>No &mdash; each one solves a specific kind of field or moment, and stacking all twelve onto one short form would be more overhead than help. A two-field newsletter signup needs little beyond field-specific errors and a loading submit button; a multi-page checkout with a password and a card number is where most of this gallery earns its place at once.</p>
<!-- /wp:paragraph -->
